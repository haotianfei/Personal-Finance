# 一个 App 一个来源组，来源组与账户为 N:M（解析组与映射前缀分离，账户另建归属）

**修订（2026-11-04，已接受）**：文中「账户（`Attribute type="account"`）」这一承载已由 **ADR-0019** 取代——账户维度改为 `institutions`（机构）/`channels`（渠道）两张专用字典表，`source_group_accounts` 关联表改指 `institutions`。来源组与账户 N:M 的关系结论不变。

截图录入的来源组改为**每 App 一个组**（如「示例钱包App」「示例政务App」「示例银行App」），作为解析配置与 CRUD 的最小单位；资产映射/清零范围仍按**窄前缀**（如 `示例钱包App-示例投顾-`、`示例钱包App-五险一金-`）圈定。一个来源组可绑定一个或多个资产前缀模板。

**来源组 ≠ 账户**：来源组是「截图/数据从哪个 App 来」的标识；账户（`Attribute type="account"`）是「钱放在哪个机构」（如示例货币基金、基金、公积金账户）的资产归属维度。二者为 **N:M**——一个来源组截图可覆盖多个账户（示例政务App截图里有公积金账户）；一个账户的资产也可来自多个来源组截图（公积金账户既从示例政务App也从其他 App 录入）。来源组与账户的绑定存于单独关联关系，不合并身份。

**Considered Options**：曾想「来源组 = 账户」合并成一套（一个 App 一个账户），但用户区分了二者：同一 App（示例钱包App）下可有多类账户（示例货币基金/基金/示例投顾），且一个账户（公积金账户）可能来自多个来源组截图。曾用「窄前缀即来源组」（现状 `bantuou` 组前缀 `示例钱包App-示例投顾-`），来源组数量爆炸且需改代码；曾考虑「一个 App 一组 + 统一宽前缀 `示例钱包App-`」，但会让「截图未出现 → 清零」误伤同 App 未截到的其它资产。最终取拆分层：解析配置粒度粗（App 级、减少维护、新 App 免改代码），映射语义粒度细（窄前缀、规避清零误伤），账户归属独立于来源组。

**Consequences**：来源组迁移为可管理实体（表 + CRUD API + 前端管理界面），源码组里相关逻辑改为读库。新增「来源组 ↔ 账户」关联（N:M）。应用层修复：`apply_preview` 写入资产时**必须挂上账户属性**（现状缺失——截图资产不挂 account，导致按账户维度分析漏收录），默认取该来源组关联的账户，前端可改。清零规则按绑定的窄前缀圈定而非组级宽前缀/账户，这是唯一需要额外谨慎的边界。

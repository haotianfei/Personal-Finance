## 1. 背景与问题

1. **C1 现无承载物**。`allocation_targets` 只有「维度 + 目标百分比 + 单阈值」三列（`backend/models.py:76-88`），没有金额、期限、目标年化、版本号、理由或审计；它的语义是 C2 的**目标占比向量**，不是 C1 的**绝对净值目标**。把金额目标塞进该表会同时污染 C1/C2 两条业务链。
2. **目标版本是已冻结的架构预留**。系统架构明确「目标（根）= 目标金额 + 期限为主锚，派生所需年化；每次变更 = 新 GoalVersion + 理由，状态：草案→生效→被取代」（`docs/design/system-architecture.md:57`）。C1 只需把该聚合落成表与端点。
3. **指标骨架已上线，C1 是下一个挂点**。注册表已含 11 项指标与灯引擎（`backend/services/metric_service.py:64-187`、`:222-251`），但没有任何 C1 项；`get_status` 只编排 B1/B2/B3/C2（`backend/services/metric_service.py:271-434`）。三期-1 的验收要求「每条需求点到具体指标」（`docs/design/metric-system.md:176`）。
4. **归属仍是记录级，且无变更史**。`asset_owners` 端点实际是 `attributes.type="owner"` 的 CRUD（`backend/routers/asset_owners.py:12-22`），归属挂在 `assets` 行经 `asset_attributes`（`backend/models.py:296-308`）；批量改归属只改所选快照行（`backend/services/asset_service.py:714-719`），同一资产项的不同记录可能各挂各的。这与「共有归属 = 资产项级当前值 + 变更留史」的冻结口径不符（`docs/design/system-architecture.md:55`、`docs/design/metric-system.md:130`）。
5. **本机只读抽查（聚合）未发现改名/多归属冲突**，但代码路径允许其发生：改名不回写历史 `asset_name`（`backend/services/asset_service.py:140-172`），而 B1 汇总按 `asset_name` 分组（`backend/services/analysis_service.py:36-77`）。C1 必须把这个已知口径风险显式化，不能假装不存在。

## 3. 目标模型

### 3.1 Goal 根（`goals`）

| 字段 | 类型 | 语义 |
|---|---|---|
| `id` | INTEGER PK | 代理身份。 |
| `name` | TEXT NOT NULL | 人读名称（「家庭净资产 2030」）；事件/用途放这里，不建 `goal_type`。 |
| `scope_kind` | TEXT NOT NULL | `family` \| `member`；本期 API 只放行 `family`。 |
| `scope_owner_id` | INTEGER NULL → `attributes(id)` | `member` 时必填；`family` 时必空。 |
| `is_primary` | INTEGER NOT NULL DEFAULT 0 | 概览/北极星用；全表至多一条 1（部分唯一索引）。 |
| `created_at` | TEXT NOT NULL | ISO。 |

- **Scope 在 Goal 根，不在版本内**：改范围=换一个目标（新 Goal），避免「同一目标忽家庭忽成员」导致达成度不可比。
- `member` 范围**设计即纳入、本期不启用**：API 对 `scope.kind="member"` 返回 422 `VALIDATION_ERROR`（field=`scope.kind`），文案「成员目标随四期启用」。这样 schema 不为四期返工，行为不半成品。
- 家庭池**不是 Goal scope**：它是归属值的一种（见 §5）；家庭目标天然覆盖家庭池、成员项与未标注项（家庭净值=全部项），成员目标（四期）才按归属过滤。

### 3.2 GoalVersion（`goal_versions`）

| 字段 | 类型 | 语义 |
|---|---|---|
| `id` | INTEGER PK | 版本行身份（审计 `row_id`）。 |
| `goal_id` | INTEGER NOT NULL → `goals(id)` | 聚合根。 |
| `version_no` | INTEGER NOT NULL | 每 Goal 从 1 单调递增；`UNIQUE(goal_id, version_no)`。 |
| `status` | TEXT NOT NULL | `draft` \| `active` \| `archived`；每 Goal 至多一条 `active`（部分唯一索引）。`archived` 同时承载「被新版本取代」与「目标归档」——由 Goal 根是否还有 active/新建版本区分，不设第四态。 |
| `target_amount` | NUMERIC(15,2) NOT NULL | **净资产**目标（资产−负债），名义 CNY，`>0`；不是总资产目标。 |
| `target_date` | DATE NOT NULL | 目标时点；`> effective_from`。 |
| `target_rate_annual` | NUMERIC(8,4) NULL | 人设目标年化（小数，0.05=5%）；仅作对齐锚点，不参与达成度公式。 |
| `risk_profile` | TEXT NULL | `conservative` \| `balanced` \| `growth`；R-19 锚点，本期不消费。 |
| `life_stage` | TEXT NULL | `accumulation` \| `transition` \| `decumulation`；分区轴①的人裁决值。 |
| `reason` | TEXT NOT NULL | R-18「设定与变更记录理由」。 |
| `effective_from` | DATE NULL | 激活时由服务端写为**激活当日**；draft 期为空。不做未来生效/回溯生效（glide path 与回溯定格分别留三期-2/4）。 |
| `criterion_json` | TEXT NULL | 激活时写入的**判据快照**（见 §3.6）；本期 `kind=null`。 |
| `created_at` / `activated_at` / `archived_at` | TEXT | ISO；后两者可空。 |

### 3.3 状态机与不变量

```
draft --activate--> active --archive--> archived
  |                    |
  +--delete(draft)     +--new version activate--> archived
```

- **唯一 active**：激活事务内先归档旧 active，再置新 active；部分唯一索引 `(goal_id) WHERE status='active'` 兜底并发。
- **active/archived 不可改内容**：只允许状态/时间戳迁移；金额/日期/利率/分区/理由写错 → 新建版本。`draft` 可改、可物理删除（删除留审计行）。
- **版本号不回退**：`version_no = max+1`；并发冲突由唯一约束转 `GOAL_VERSION_CONFLICT`（409）。
- **不变量 6**：任何 Goal/Version 只能由人触发用例创建；没有系统自动改目标的路径。C4/R-30 的「反哺」也只是提案，采纳=人调用本端点。
- **归档终态**：Goal 归档 = 其所有未归档版本置 `archived`；不提供 unarchive；归档后不再接受新版本/激活，要重启就新建 Goal。`is_primary` 归档时清零，概览回退到最近激活的 active 目标（无则无 C1 指标）。**只有带 active 版本的 Goal 才能是主目标**；draft-only Goal 的 `is_primary` 恒 0。

### 3.4 Goal 类型：只做「金额 + 时点」，不建多态

| 候选 | 处理 | 理由 |
|---|---|---|
| 金额目标 + 期限 | **唯一一等形态**；`target_amount` + `target_date` | 拍板 2：金额+期限为主锚（`business-architecture.md:240`）。 |
| 目标年化收益率 | `target_rate_annual` 可选列，不是独立类型 | 拍板 2「两者兼有」，年化只作对齐锚点；纯收益率目标无法算缺口/所需年化。 |
| 比例目标（如「权益 ≥60%」） | **归 C2** `allocation_targets`，C1 不建 | 比例是配置权重，不是净值目标；两套口径混用会让「达成度」失去分母。 |
| 事件目标（买房/教育） | 用 `goals.name` 表达，不建事件实体/类型 | 事件在数据上仍是「某日期前达到某金额」；建类型只增加分支，不增加信息。 |

**结论**：不建 `goal_type` 枚举，不建 `goal_events` 表。若未来出现「纯收益率目标」的真实需求，再以新版本/新 ADR 评估；本期不预留多态字段。

### 3.5 与 `allocation_targets` 的关系：并存，不迁移、不取代

| 维度 | `allocation_targets`（C2） | `goals` / `goal_versions`（C1） |
|---|---|---|
| 语义 | 某维度上的**目标占比**（fund_type / liquidity_rating / account） | **绝对净资产金额** + 期限 |
| 结构 | 一行一个维度项，`parent_id` 层级，`target_percent` + `alert_threshold`（`backend/models.py:76-88`） | 一根多版本，版本不可变 |
| 变更 | 现为原地更新/删除，无版本、无理由（`backend/services/allocation_service.py:31-37`、`:104-147`） | 新版本 + 理由 + 审计 |
| 消费 | `analyze_allocation` / 配置偏离（`backend/services/allocation_service.py`、`metric_service.py:530-561`） | 达成度族 / 概览北极星 |
| 本期动作 | **零改动** | 新建两表 + 端点 |

- **不设外键**：GoalVersion 不引用 AllocationTarget，AllocationTarget 也不引用 GoalVersion。C2/三期-2 若需要「框架实例挂在目标版本下」，再加 `framework_instance.goal_version_id`；现在加会提前绑定两套尚未合并的版本模型。
- **不迁移数据**：现有 target 行是权重，没有可推导的金额/期限；强行生成 Goal 是伪造人裁决。
- **不取代**：C1 上线后 `allocation_targets` 仍是 C2 的唯一目标占比真源；两者在 UI 上分属「目标」与「配置」两页。

### 3.6 分区轴①：生命周期阶段/风险档 = GoalVersion 上的受控枚举

> **术语对齐**：`metric-system.md:116-123` 的四轴里，轴①是「目标版本」、轴③是「风险偏好档」。本节**不新增第五轴**：把「生命周期阶段/风险档」作为 GoalVersion 上的**版本化属性**，与目标版本由同一个 active 版本解析器一并返回；语义上仍落在「目标版本」这把尺下，因此 `band_basis` 恒 `current`。风险档不改变 §5 的轴③定义，只是提前把它挂到版本上，供 C2/R-19 消费。

**决策**：`risk_profile`、`life_stage` 作为 **GoalVersion 的可空枚举列**，人裁决设定；**不建表、不派生、不做阈值迁移表**。解析函数为纯函数：

```
resolve_partition(version) -> {
  goal_version_id: version.id,
  risk_profile: version.risk_profile,      # null | conservative | balanced | growth
  life_stage: version.life_stage,          # null | accumulation | transition | decumulation
  band_basis: "current"
}
```

- **为什么不是表**：两轴都是闭集单值，且已经随 GoalVersion 版本化；独立表只增加 join 与第二套版本，不增加表达能力。
- **为什么不是派生**：生命周期阶段不能从年龄/目标日期可靠推出（账本没有出生年月/收入/负债结构）；派生等于发明数据，违反「目标由人设定」（不变量 6）。
- **为什么不放 `attributes` 树**：属性树服务资产分类（`CONTEXT.md:41-55`），不是目标设定；放进去会让「所有者/类型」与「风险档」共用一个可增删的字典，语义漂移。
- **与 `band_basis` 的关系**：本期所有 C1 读路径都在请求时解析**当前 active GoalVersion**，因此 `band_basis` 恒 `current`；`criterion_json` 只是把激活时的分区/判据定格下来供审计与三期-4 重放，**不用于 as-of 历史解析**。历史版本解析（`band_basis="as-of"`）留三期-4（`docs/design/metric-system.md:106`、`:185`）。
- **变更即新版本**：改 `risk_profile`/`life_stage` 即使金额不变，也新建 GoalVersion；否则「当时的尺」无法解释。
- **本期计算不消费**：C1 达成度公式不按风险档分支；它们只作为 C2/R-19 的输入与复盘标签。这样避免把「风险偏好 → 建议配置」的半成品塞进 C1。

### 3.7 判据快照与「无判据」

`criterion_json` 在激活时写入，形状固定：

```json
{"schema":1,"kind":null,"band_basis":"current",
 "partition":{"risk_profile":"balanced","life_stage":"accumulation"},
 "note":"C1 no default band; grade=null until 三期-2"}
```

- **为什么有快照**：判据/分区是「当时的尺」；即使本期 `kind=null`，也要把「这一版明确没有判据」固化，防止未来补默认带时反写历史。
- **为什么本期 `kind=null`**：指标系统冻结「本期仅实现偏离类绝对阈值；红档、相对带、双阈值随三期-2；无判据则 `grade=null`，不发明默认带」（`docs/design/metric-system.md:104`、`:172`、`metric_service.py:234-238`）。达成度的判据属于「目标进度偏离」，归 B4/三期-2；C1 只出值。
- **读端不使用快照做求值**：`criterion_json` 是审计/重放材料；当前求值只看「有没有判据」——本期没有，所以 `grade=null`。

## 4. 达成度指标族

### 4.1 定义与公式

记号：`NW(as_of)` = 截至 as_of 的净资产（资产侧沿用值之和 − 负债侧沿用值之和）；`T` = `target_amount`；`D` = `target_date`；`d = D − as_of` 的天数。

| id | 显示名 | 公式 | 单位/精度 | 方向 | 判据 |
|---|---|---|---|---|---|
| `goal_progress` | 目标达成度 | `NW / T` | ratio，4 位小数 | 越高越好 | null（本期） |
| `goal_gap` | 目标缺口 | `T − NW`（负=盈余） | CNY，2 位小数 | 中性 | null |
| `goal_required_annualized` | 所需年化 | 见下 | ratio，4 位小数 | 中性 | null |

`goal_required_annualized` 分段：

```
if gap <= 0:                    0.0000
elif NW <= 0:                   null  + RATE_UNAVAILABLE（阻断）
elif remaining_days <= 0:       null  + RATE_UNAVAILABLE（阻断）
else:                           (T / NW) ** (1 / remaining_years) - 1
remaining_years = remaining_days / 365.25
```

`details` 同时给 `remaining_days`、`remaining_months`（按日历月差，目标日小于 as_of 时为 0/负值并附注），避免把「剩余期数」做成第四个指标而引入新的单位格式。

### 4.2 口径（必须写进响应 details / meta）

- **净值含负债**：`NW = Σ资产 − Σ负债`，与 B1 同源；目标金额按**净资产**理解。负债项不单独设目标。
- **现值、名义**：全部为名义 CNY，不做通胀调整、不做汇率换算（单币种账本假设）；`details.basis` 写明 `nominal_net_worth`。
- **as-of 沿用**：与 `analysis_service._sum_as_of` 完全同口径（截至 as_of 每项最近有效行，未更新沿用，不置零）；不另造一套净值。
- **同一 as_of 对账**：`/api/metrics/status` 的 `net_worth`、C1 的 `NW`、`/api/analysis/summary` 必须同值（指标骨架既有验收，`metric-system.md:168`、`.scratch/metric-skeleton/spec.md:55`）。
- **舍入**：金额 2 位、比率 4 位，`Decimal` 字符串；所需年化先按未舍入值计算，最后 quantize。
- **所需年化的假设**：`(T/NW)^(1/年)−1` 是「不再追加/撤出本金」的 CAGR 门槛；账本没有收入/储蓄计划，故不建模未来现金流。目标页必须注明「假设不再投入」，否则用户会把门槛误读为预测。
- **空库且未给 as_of**：`NW=0`，`meta.snapshot_date=null` + `NO_DATA`；剩余期数按今日显示并在 `details` 注明口径，不把它伪装成历史快照。
- **不比较已实现收益**：本期不把 XIRR/TWR 塞进达成度；B2 的 `xirr` 已单独暴露。目标页可并列展示，但公式不混。

### 4.3 与指标注册表 / `metric_service` 的挂点

- 注册表新增 3 条：`domain="C1"`、`criterion=None`、`as_of_semantics="时点(as-of)"`、`drill.target="/planning/goals"`。标签按 `metric-system.md:78-87`：`goal_progress` 派生/比率/时点/越高越好/展示/派生；`goal_gap` 派生/金额/时点/中性/诊断/派生；`goal_required_annualized` 派生/比率/时点/中性/诊断/派生。
- `get_status` 在 B1/B2/B3/C2 之后追加 C1 candidates：仅当存在**可解析的有效目标**（`is_primary` 的 active 目标；无主目标时回退到最近激活的 active 目标），且 `effective` 为空或 `>= effective_from`；否则不出现 C1 项（与「无目标→无行」的既有先例一致，`metric_service.py:530-536`）。`details.is_primary` 标明本次用的是不是主目标。
- 目标页 `/api/planning/goals/{id}/progress` 与 `get_status` 共用**同一个纯函数**（建议 `goal_service.compute_progress`），避免两处公式漂移。
- `details` 形状（稳定契约）：

```json
{"goal_id":1,"goal_version_id":2,"version_no":2,"is_primary":true,
 "scope":{"kind":"family","owner_id":null},
 "target_amount":"1000000.00","target_date":"2030-12-31","target_rate_annual":null,
 "net_worth":"420000.00","gap":"580000.00","progress":"0.4200",

```

### 4.4 无判据 / 无目标 / 无数据的降级

| 情形 | 行为 |
|---|---|
| 无任何 active Goal | **不出现 C1 项**；`/api/metrics/status` 其余项照常；前端显示「设目标」CTA。不加新降级码。 |

## 5. 归属收口：记录级 → 资产项级（ADR-0011 摘要）

### 5.1 现状证据

- 所有者是 `attributes.type="owner"` 的行，不是独立表；端点只做字典 CRUD（`backend/routers/asset_owners.py:12-22`、`backend/models.py:273-293`）。
- 归属挂在**快照行**：`asset_attributes(asset_id, attribute_id)`（`backend/models.py:296-308`）。批量改归属只改所选记录（`backend/services/asset_service.py:714-719`），列表过滤也按记录属性（`asset_service.py:333-340`），导出按行取 owner（`backend/services/export_service.py:92-100`）。
- 因此同一资产项的不同快照可以各挂不同 owner；没有变更史，无法回答「何时改的、为什么」。
- 删除 owner 只检查 `asset_attributes` 使用数（`backend/routers/asset_owners.py:108-119`）；收口后必须同时检查新表，否则会留下孤儿引用。

### 5.2 目标形态（`asset_item_owner_changes`，append-only）

| 字段 | 类型 | 语义 |
|---|---|---|
| `id` | INTEGER PK | 变更行身份。 |
| `asset_item_id` | INTEGER NOT NULL → `asset_items(id)` | 聚合根。 |
| `owner_kind` | TEXT NOT NULL | `member` \| `family_pool`。 |
| `owner_id` | INTEGER NULL → `attributes(id)` | `member` 必填；`family_pool` 必空。 |
| `effective_date` | DATE NOT NULL | 本期写当日；补录/回溯留四期。 |
| `reason` | TEXT NULL | 人读理由；审计另有 before/after。 |
| `origin` | TEXT NOT NULL | `manual` \| `migration`（预留 `import`/`screenshot` 可归入 manual）。 |
| `created_at` | TEXT NOT NULL | ISO。 |

- **当前值不落列**：当前归属 = 按 `(effective_date DESC, id DESC)` 取最新一行；**无行 = 未标注**。这与本金口径「变更史权威、无双真源」同构（`CONTEXT.md:157-159`、`models.py:135-160`），避免 `asset_items.owner_id` 与史表双写。
- **家庭池**：`owner_kind="family_pool"` + `owner_id=NULL`；不建「家庭池」属性行，避免用户重命名/删除虚拟成员。UI 显示固定「家庭池」；owner 字典禁止创建/改名为「家庭池」，防止语义碰撞。
- **单值**：一个资产项同时只有一条当前归属；共有一律家庭池，不做比例拆分（拍板 6，`business-architecture.md:244`）。**本期不支持「清空为未标注」**：要取消成员归属就设家庭池；空值请求按「不改变」处理，避免误清空。
- **append-only**：存储层 BEFORE UPDATE/DELETE 触发器 `RAISE(ABORT)`，与 `principal_changes` 同模式（`migrations/0012_principal_basis.py:35-47`）；更正=追加新行。

### 5.3 读写路径与兼容

**写（canonical）**：`POST /api/asset-items/{item_id}/owner`，body `{owner_kind, owner_id?, reason?}`；服务内 `set_item_owner()` 追加一行 + 审计，同一事务。归档项拒绝（`ITEM_ARCHIVED` 409，沿用 `backend/services/principal_service.py:85` 先例）。

**兼容写**：
- 现有 `PUT /api/assets/{id}` / 批量 `owner_id` / `attribute_ids` 中的 owner 项，在一个兼容版本内**翻译**为 canonical 写入：按 `record_ids → asset_item_id` 分组，每项调用 `set_item_owner`；不再写记录级 owner 关联。返回体附 `owner_scope:"item"` 提示。
- 前端 `records` 页的批量改归属改文案「归属按资产项生效」；单条编辑同样走 item 级。兼容期结束后删除翻译层与记录级 owner 写入。
- 截图/导入：只在**新建资产项**时按模板/CSV owner 写一次初始归属；已存在项不自动覆盖（避免导入把人工归属改掉）。冲突在预览/导入结果里标 `owner_conflict`，由人裁决。

**读**：
- `build_asset_response` 先取 item 级当前归属，取不到再回退记录级 owner（兼容旧数据）；响应新增 `owner_kind`，`owner_id/owner_name` 保持原字段（family pool 时 `owner_id=null`、`owner_name="家庭池"`）。`backend/routers/assets.py:96-97`。
- `list_assets` 的 `owner_id` 过滤改为 item 级当前归属（子查询），兼容期可 OR 记录级；新增可选 `owner_kind` 过滤（`member`/`family_pool`）。
- 导出按 item 级归属输出，同一项所有行一致（`export_service.py:92-100`）。
- 不做双写：item 级是唯一写源，记录级只读回退。理由见 §7「方案对比」。

### 5.4 数据迁移（0016）

- **回填来源**：每个 `asset_item` 的最新 active 快照行（`superseded_by IS NULL`，按 `asset_date DESC, id DESC`）上挂的 owner 属性；若一行多 owner，按 `asset_attributes.created_at DESC, attribute_id DESC` 取最后挂上的一个（确定性 tie-break）。**不回退到更早记录**：最新行没有 owner 就按未标注处理（宁可让用户重挂，也不臆造归属）；「最新无 owner 但更早有 owner」列入迁移前 `owner_lost_candidates` 清单供人工复核。
- **effective_date = 迁移当日（本地时区）**，`origin="migration"`，`reason="migration: latest active record owner"`。不伪造历史生效日；四期若要做成员 as-of 视图，再用记录级历史做单独回填/评估。
- **无 owner 的项不插行** = 未标注；迁移不创建家庭池行。
- **保留名**：迁移前检查是否已有 owner 名为「家庭池」；命中则 fail-fast，提示先用旧 UI 改名（否则合成家庭池与成员同名，语义冲突）。
- **冲突**：多 active 记录 owner 不一致时取最新 active 行；迁移前用只读查询列出冲突清单（不阻塞迁移）；0016 在迁移事务内写一条 `schema/owner_backfill` 审计行（actor=system，仅本次 `changes>0` 时写），`after` 含 `items_with_owner/changes/conflicts/owner_lost_candidates` 计数。当前本机抽查无冲突，但脚本必须处理。
- **幂等**：`CREATE TABLE/INDEX IF NOT EXISTS`；回填按 item `NOT EXISTS`（空表时等价全量）；整个升级单事务（runner 语义，`db_migration_service.py:113-131`）。
- **回滚**：不 UPDATE/DELETE 任何旧表；revert 代码后旧读路径仍可用。新表残留无害。

### 5.5 回滚边界

- 前向兼容：新代码读旧数据（回退记录级）✅。
- 后向兼容：旧代码读新数据——迁移后记录级属性仍在，旧代码可显示旧归属；但**切换后的人工归属编辑不会回写到记录级**，回滚后旧 UI 看不到这些编辑。接受此降级：不丢账本事实，只丢归属展示；单用户本地应用可人工修正。
- 不选「双写」：会让 item 级与记录级成为双真源，长期必然漂移；与 `CONTEXT.md` 的本金口径纪律相悖。

## 7. 方案对比

| 方案 | 内容 | 优点 | 缺点 | 工作量 |
|---|---|---|---|---|
| **A 最小可行** | 单张 `goals` 表存当前目标（金额/日期），无版本；达标度 3 指标；归属不动 | 最快；1 迁移；前端 1 页 | 违反 R-18 版本留史；目标改动不可追溯；归属问题留到四期，届时要重做数据迁移；C4 无锚点 | **S**（1~2 波） |
| **B 完整** | A + GoalVersion + member scope 计算 + 归属收口 + 分区表 + 判据带 + C2 目标权重联动 + C4 定格 | 一次到位；未来无需再动模型 | 越过三期-1 边界；member 视图/家庭池生命周期未定义；C2/C4 设计未冻结，必然返工；迁移与测试面大 | **L**（8+ 波） |
| **C 渐进（推荐）** | Goal+GoalVersion；只放行 family scope；member/分区/判据留列与解析缝；归属收口独立波；C2/C4 不碰 | 满足 R-15/R-18 与三期-1 验收；版本史/审计/回滚完整；未来 C2/C4 有稳定锚点；范围可控 | 本期没有成员目标、没有灯、没有历史 as-of；归属兼容期双读路径增加测试面 | **M**（5 波） |

**推荐 C**。关键理由：C1 的不可逆成本在**数据模型**（目标版本、归属史），不在页面；A 省掉的正是不可逆部分，B 把未冻结的 C2/C4 提前固化。C 把「必须现在对的」做对（版本、审计、归属），把「可以以后加的」留成列/纯函数缝。

## 9. 验收（C1 完成的定义）

1. **R 映射**：§2.2 每行都有「表/指标/端点」或明确的「三期-2/4」；不存在「声称做了但无承载」的行。
2. **目标版本**：创建→草案→激活→归档全链路；同一 Goal 永远 ≤1 active；active/archived 不可改内容；每次写有审计；同键重放不双写。
3. **达成度**：3 项指标在 `/api/metrics/status` 与 `/goals/{id}/progress` 同值；同一 as_of 与 B1 `net_worth` 同值；无目标不出现；空库/部分录入/率不可得降级正确；无判据 `grade=null`。
4. **归属**：迁移后每个有 owner 的资产项恰有一条当前归属；列表/导出/记录页显示 item 级；旧批量入口翻译为 item 级；owner 删除保护含新表；回滚演练通过。
5. **迁移/备份**：0015/0016 在真实库副本上幂等重跑通过；迁移前自动备份存在；无 down 但 revert 后旧代码可启动。
6. **安全**：`bash scripts/check-public-safety.sh` 通过；文档/测试/日志无真实财务数据、主机名、内网 IP、本机绝对路径、密钥。

## 10. Considered Options（为什么不是别的）

- **把金额目标加到 `allocation_targets`** → 弃：该表是权重 + 单阈值，无版本/理由/期限；混用会让 C2 偏离与 C1 达成度共享一行，任何一方变更都污染另一方（`models.py:76-88`、`allocation_service.py:31-37`）。
- **单行可变 Goal，不做版本** → 弃：违反 R-18「变更记录理由、版本留史」与不变量 8；C4 无法回答「当时的目标是什么」；补版本要重写数据。
- **多态 Goal（金额/比例/事件/收益率）** → 弃：比例已有 C2 真源；事件在数据上=金额+日期；纯收益率无法算缺口。多态只增加分支与空字段。
- **分区建独立表/阈值迁移表** → 弃：两轴是闭集单值且随 GoalVersion 版本化；建表是第二套版本，本期无消费方（YAGNI）。
- **生命周期阶段自动派生** → 弃：账本无出生/收入/负债结构，派生=发明数据，违反不变量 6。
- **归属双写（item + 记录级）** → 弃：双真源必然漂移；与本金口径「变更史权威」纪律冲突（`CONTEXT.md:157-159`）。
- **归属只做读时合并、不建史** → 弃：无法回答「何时改的/为什么」，也无法支撑四期成员 as-of 视图；R-31/R-32 的「明确归属规则」需要可追溯。
- **C1 一次做到 C2/C4** → 弃：C2 双阈值/框架实例与 C4 信息集定格尚未冻结；提前固化会返工，且越过三期切片（`metric-system.md:168-178`）。

## 11. Consequences

**正面**

- C1 有可执行的最小闭环：设目标→看达成度→版本可追溯；R-15/R-18 真正落地，R-17/19/20/21/28/29/30 有明确锚点与切片归属。
- 目标/归属都进入「人裁决 + 版本/变更史 + 审计」的同一纪律，C4 复盘与四期成员视图有稳定数据基础。
- 不动物价/汇率/流水，不破坏台账边界（`metric-system.md:8-20`）。

**负面/代价**

- 新增 3 张表、2 个迁移、1 个新 API 家族、1 个新页面 + 概览卡；归属兼容期有双读路径与测试面。
- 本期没有成员目标、没有灯、没有历史 as-of 目标；用户可能觉得「目标页只有进度，没有建议」——这是切片边界，不是缺陷。
- `criterion_json` 本期是「无判据快照」，看起来“空转”；它是为三期-2/4 防反写，必须保留。

**后续（不在本 ADR 决策内）**

- W0 P0：`_sum_as_of` 按 `asset_item_id` 分组（改名正确性）。
- 三期-2：C2 双阈值/相对带/框架实例/域级汇总；`allocation_targets` 版本化。
- 三期-3：hash-chain 回填，覆盖新增 action。
- 三期-4：`band_basis="as-of"` 解析、C4 复盘/归因/反哺；成员目标启用。

## 12. 需业主拍板

1. **Goal 形态**：只做「净资产金额 + 期限」，比例归 C2、事件用名称、纯收益率不单独建模——是否同意？
2. **成员 scope**：三期-1 只留列、API 422（四期启用），还是本期就放行成员目标计算？
3. **归属收口**：家庭池用 `owner_kind="family_pool"` 合成值（不建属性行）、不做双写、回滚接受「归属编辑不回写旧 UI」——是否同意？
4. **P0 前置**：是否批准把 `analysis_service._sum_as_of` 的 name→item 修正作为 C1 前的独立 P0（推荐批准；否则改名后达成度可能双计）？
5. **ADR 拆分**：发布时拆 ADR-0010（C1）/ ADR-0011（归属），还是合并一篇？

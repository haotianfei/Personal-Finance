# ADR-0024：凭证按来源组去重与复合唯一索引

- **状态**：已接受（2026-11-06，业主签字）
- **日期**：2026-11-06
- **上游**：ADR-0022（凭证文件命名与图像元数据）
- **下游**：迁移 `0033_dedupe_evidence_sha_group.py`

## 背景

`screenshot_evidence` 现有 28 行、23 个不同 sha，其中 5 组「同 sha 两行」。查证结果：**每组两行的来源组相同**，即同一张图在同一组被传了两次；每组恰有一行被账本引用，另一行在 `assets` / `audit_log` / `principal_changes` / `transfer_events` 四类引用全为 0，两份文件都在盘上（合计 4.23 MB）。

数据库层没有唯一约束，是因为查重一直只在应用层做（`get_or_create_evidence` 先按 sha 查、命中就返回旧行）。

而这条应用层查重是**全局**的：同一张图上传到**另一个来源组**时，会静默复用第一个组的凭证行——凭证的 `source_group_id` 因此与事实上传的组不符。文件名里的 `sg<id>` 也就跟着错。这在此前不成问题（单组使用为主），但命名规范化之后，文件名把组 id 变成了可见的事实声明，错误归属会一直摆在那里。

## 决策

1. **查重范围收窄到「同组」**：`(file_sha256, source_group_id)` 唯一确定一行。同图属两组 → 两行、两份文件，各带自己的 `sg<id>` 名。
2. **唯一约束也随之复合**：`UNIQUE INDEX ux_screenshot_evidence_sha_group (file_sha256, source_group_id)`。
3. **存量 5 行零引用重复行在迁移 0033 里删掉**，判据从严（同组有同学、四类引用全 0），保留引用最多的一行。删除前打印清单、删除后对账。
4. **文件不随迁移删**：迁移只删行，留下的 5 个孤儿文件由脚本报告、业主备份后删除。

## 否决的方案

- **单列 `file_sha256` 唯一索引**：与「一图可属两组」直接冲突。若同时保留全局查重，第二组永远拿不到自己的凭证行；若改成同组查重，索引立刻拒绝插入。两种组合都不成立。
- **只删重复行、不加索引**：应用层查重仍是唯一防线，一旦有并发或旁路写入（脚本、迁移、手工 SQL）重复就会回来——正是这批历史数据产生的方式。
- **保留全局查重、不建索引**：等于承认「B 组的图算 A 组的凭证」，与命名规范化后的可见事实矛盾。
- **迁移里连文件一起删**：事务管不了文件系统，回滚后行回来了文件却没了，比留着孤儿更糟。
- **建「一图多组」关联表**：把凭证行与归属解耦，模型上更灵活，但当前没有「一张图要同时归属多个组」的真实需求，为假想需求改模型不值得。

## 代价

- 同一张图跨组上传会**存两份文件**（磁盘翻倍）。以当前体量（单张百 KB 至几 MB）可接受；真出现跨组复制需求再评估内容寻址。
- 迁移要删数据，虽判据从严且有备份，仍是不可逆动作；执行前必须备份，且迁移只删「四类引用全 0 且同组有同学」的行。
- `ux_screenshot_evidence_sha_group` 一旦建立，任何绕过应用层塞重复行的脚本都会立刻失败——这是想要的效果，但意味着相关脚本需要知道这条约束。
- 5 个孤儿文件需要人在迁移后手工清理，迁移与文件清理之间存在一段不一致窗口。

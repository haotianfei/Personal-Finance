## 1. 问题

`assets.asset_name` 是**写入时的显示名快照**（`models.py:847`，时点语义），而身份是 `asset_item_id`。两者在改名后必然分叉：

1. 截图录入按「机构前缀 + OCR 名」做文本匹配（`get_group_existing` + `fuzzy_match_name`），识别名与库内写法不同（分隔符、期号、尾号、口语简称）就判成新增——实测现役 66 对近似命名里 **61 对（92%）双向都匹配不上**，都会静默新建一个重复资产项，钱被算成两笔。
2. 改名端点只写名史 + 改 `display_name`，历史快照文本不动；一旦改名，按名回查（趋势、告警、历史详情）就查不到旧行。而「旧名本来就是写错的」这种情形，留着错名反而是留脏。

这两个问题的共同根源是：**名字被当成了身份**。

## 2. 决策

### D1 录入侧的「关联到已有项」是一个显式的行级裁决 `bind`

`POST /api/screenshots/apply` 的 `options.identity_decisions` 增加第三种动作：

```json
{ "<行号>": { "action": "bind", "target_item_id": 42 } }
```

语义：这一行的钱写进**已有**资产项 42，`display_name` 不动、不建血缘、不归档任何前身、`id` 不变；同时把该行最终名（前缀 + OCR 名）作为**别名**沉淀到名史（`origin='alias'`）。

刻意不叫 `link`（与 `lineage_links` 撞词），也刻意不复用既有 `merge`：`merge` 是「新旧两个项合并」，会新建后继项并归档前身，`id` 前移——正是业主不要的那种「id 变了」。

### D2 新增行必须显式表态，不再默认新建

凡是 `action='create'` 的行（以及带 `identity_guess` 的行），必须逐行给出 `create` 或 `bind`。缺任何一行，整批 400 `IDENTITY_DECISION_REQUIRED` 且**零写入**（连凭证都不建）。

这条是为「静默新建」上闸：默认采纳 OCR 名字，等于让机器替人决定「这是一笔新资产」。前端配套「本批全部确认新增」一键表态，把摩擦压到一次点击。

### D3 名史扩为「三类行 + 两个语义列」

`asset_item_names` 重建（迁移 0035）后：

| 列 | 语义 |
|---|---|
| `origin` | `migration`（历史导入）/ `rename`（改名留下的旧名与新名）/ `alias`（别名） |
| `effective_from` | `rename`/`migration` 必填；**`alias` 必须为空**（别名不设生效区间） |
| `reason` | `correction` / `evolution` / `normalization`，可空 |
| `effect` | `current` / `history_backfill`，可空 |
| `reason_note` | ≤200 字，破例时必须写理由 |

存量 146 行 `reason`/`effect` 一律 `NULL`，意思是「不知道」，不倒填一个假原因；解析层把 `effect IS NULL` 视同 `current`。新写入由应用层强制带值，不靠 DB 默认值兜底。

别名不建独立表：别名与历史名都是「这个实体曾经/也可以叫这个名字」，一张表两个 `origin` 足够；独立表会带来两套解析与两套唯一性规则。

### D4 改名两步走：先预览影响面，再带令牌执行

- `POST /api/asset-items/{id}/rename/preview` → 返回影响面（行数、日期跨度、其中 superseded 行数、目标项是否已归档）+ 一次性 `confirm_token`（TTL 10 分钟），令牌绑定 item + 目标名 + reason + effect + note + 影响面哈希；
- `POST /api/asset-items/{id}/rename` 带令牌执行，事务内**再判一次撞名**、比对影响面哈希；令牌已用/过期/载荷不符/影响面已变 → 409 `RENAME_CONFIRM_INVALID`。

为什么必须两步：`correction` 会改写整段历史的名称文本，这是不可逆动作。把「有多少行会被改」先摆到人眼前，是这个决策的全部价值；一个只有 `rename(name)` 的端点等于让人闭眼按下去。

### D5 `effect` 决定动不动历史：`current` 是常态，`history_backfill` 是破例

- `evolution`（名称演进：产品改名、机构更名）→ 默认 `current`：只改当前显示名，历史快照保持当时文本。历史是「当时看到的名字」，改动它就等于伪造时点事实。
- `normalization`（书写归一：分隔符、全半角、多余空格）→ 默认 `current`。
- `correction`（旧名写错了）→ 默认 `history_backfill`：旧名本身就是错的，留着它只会让「按名回查」继续找不到东西。

选非默认组合（例如「拼写修正但只想改当前名」）必须写 `reason_note`，否则 400 `RENAME_NOTE_REQUIRED`。破例可以，但要说出为什么。

### D6 撞名判定按归一后的三层名，自己的旧名不算

目标名经 `_cmp_norm` 后与**任何其他资产项**的现名/历史名/别名相同 → 409 `NAME_CONFLICT`，回带冲突项 id 与命中的层。

- 三层都查：历史名与别名同样要能解析回项，只查 `display_name` 会留下「改名成功但解析歧义」的后门；
- 自己的历史名不算撞名——撤销改名的唯一通道就是「再改回旧名」，这条必须留着；
- 预检时判一次、事务内再判一次（并发窗口）。

### D7 解析收敛到单点 `name_resolution_service`，本轮只收口新路径

新增 `services/name_resolution_service.py`：给一个名字，按 **现名 > 历史名 > 别名** 返回唯一项 / 歧义候选 / 不认识。改名撞名判定与录入绑定共用这一处，避免「两个地方两套规则」。

**本轮不做**的是全仓 94 处按名调用的整体改造（票 02 的 C 类清单：分析趋势、告警、历史详情等）。那些路径目前仍按 `asset_name` 文本聚合，在 `current` 类改名下会产生「旧段按旧名、新段按新名」的断点——这是已知缺口，登记为后续项，不在本轮夹带。

### D8 `assets.asset_name` 的时点语义被有条件地破例

`models.py:847` 写着「改名不回写」。D5 的 `history_backfill` 是**有意的例外**：只在人明确选择「旧名是错的」时发生，且必须留审计。除此之外一切路径继续遵守原契约。

回写范围＝该 item 的**全部** `assets` 行（含 `superseded_by` 非空的行），不分日期；同时 bump `assets.updated_at`，让人能分辨「哪些行被这次纠正碰过」。

### D9 一条审计事件承载整次改名

`audit_log` 追加 `entity='asset_item', action='rename'`：`before` 记旧 `display_name` 与追加前的名史最大 id，`after` 记新名、reason、effect、note、**回写行数**与新增名史行 id。

名史行本身也带 reason/effect，但那是「这一类名字的来历」；审计事件才是「这一次操作」。两者不互相替代，也不把 from/to 在审计里重复存一遍——名字的区间与来历归名史行。

## 3. 否决的方案

| 方案 | 否决理由 |
|---|---|
| 独立 `asset_aliases` 表 | 别名与历史名是同一种「也叫这个名字」的关系，拆两张表＝两套解析、两套唯一性、两套迁移；`origin` 一个枚举足够。 |
| 复用 `lineage_links` 表达改名 | 血缘是「谁承接谁的钱」，会前移 id、会归档前身；改名不改身份。语义混用后，任何按 link 类型做的口径计算都会被改名污染。 |
| 只在前端做「关联」，后端不记录 | 别名、审计、后续解析都需要服务端事实；前端记忆刷新即失，且换个客户端就没了。 |
| 把 reason 塞进 `reason_note` 自由文本 | 无法聚合、无法据此决定 effect、无法在 UI 上给默认值；自由文本留作补充说明即可。 |
| 改名自动把旧名沉淀成别名 | 别名会让「旧名仍能解析到本项」，`evolution` 场景下这是错的（新旧是两个叫法，但旧名不该继续参与录入匹配）；别名只由 `bind` 产生。 |
| 影响面回写做成后台任务 | 单人单库、单事务能覆盖的数据量（当前最大 60 行/项）；异步化会引入「改成了一半」的中间态与重试幂等，收益不抵成本。 |
| 静默兼容无 reason 的旧调用 | 让「没写原因」也能成功，等于这个字段永远不会被填。宁可让旧客户端报错，也不让契约退化。 |
| 为改名补造历史审计 | 发现 13 次改名是原始 SQL 订正、审计缺失（票 02 G4b）。补造审计＝伪造证据；只记录「历史上曾有未留痕的人工订正」这一事实。 |

## 4. 代价

- `asset_item_names` 一次表重建（SQLite 改 CHECK 只能重建）；迁移前后逐项校验行数、列形状、索引与触发器，失败即回滚。当前 146 行——这是本项目少有的「行数很小、风险不低」的迁移。
- 新增 `asset_item_rename_tokens` 表与清理义务：`used_at`/`expires_at` 之外不做自动清理，长期会积行（单人使用量极小，暂不引入定时任务）。
- `create` 行强制表态会让旧前端在未升级时整批 400。这是刻意的破坏性变更：前后端必须同版本发布（本项目单机部署，同时构建）。
- 全仓按名聚合的路径仍有断点（D7 已声明），`current` 类改名在趋势图上可能看到台阶。
- 历史回写后，「当时看到的名字」不再可从账本还原，只能从名史与审计追溯——这是 `correction` 的固有代价，也是它必须两步确认的原因。

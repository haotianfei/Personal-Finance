## 1. 问题

ADR-0007 写的是「任何新写入用例必须产 change dict 并 `record()`，否则不算合法写入」。现实已分叉：

1. `app.routes` 实测 **131 个写端点**，留痕的约 20 个。账本批量删除（`asset_service.py:1187` 硬删）docstring 声称有审计、实际没有；导入、恢复整库、分类法、密钥轮换全部无声。
2. 无从判断「哪些写入该留痕」——没有判定口径，于是每加一个端点都是自由心证。
3. `entity`/`action` 是自由字符串（54 处调用点、硬编码字面量仅 2 个），无法枚举、无法校验、无法给筛选器下拉。
4. `before/after` 是无差别整段 JSON：`llm_providers` 的密钥轮换若入审计会把明文写进**不可删**的行。
5. 没有任何自动化守卫，缺口只能靠人工发现（现状 131 : 20 就是证据）。

## 2. 决策

### D1 判定规则＝五类桶

写入凡改变下列任一项，必须留痕；否则不算合法写入：

| 桶 | 含义 | 典型端点 |
|---|---|---|
| ①值 | 账本数字及其行 | assets 批量增删改、imports、expenses、transfer_events、allocations、goals |
| ②口径 | 改变同样数据如何被分组的元数据 | classification（15）、expense-categories/templates（6）、source-groups/parse-rules/guide-image、correction-rules（4）、alerts 阈值 |
| ③出处 | 凭证与其识别结果的采纳/更正 | screenshots/apply（已有）、evidence 删除（已有）、supplements/resolve |
| ④离场 | 数据离开系统 | export-history/history 与 rules、auto_export |
| ⑤整库 | 这库是哪一版 | backup/restore、backup/upload-db |

### D2 豁免只有两类，且必须登记

- 缓存/派生态：`preview_jobs`、`screenshots/preview`、`verify`；
- 派生字段回写：`PATCH /api/screenshots/evidence/{id}/recognition`（写 `recognition_json`，可从凭证重算）。

豁免写进契约表并附理由与登记日期；**新增豁免＝改契约**，不是「忘了写」。

### D3 批量写＝批次头 + 逐行明细

- 头行：`entity='batch'`、`action='execute'`、`after={op, count, ids_hash, scope}`；
- 明细行：业务 entity/action，逐行一条，快照只留关键字段（id/日期/金额/分类/owner/凭证 id）；
- 头行答「这是哪次操作」，明细答「我这一行怎么没的」；
- 界面型批量端点单次上限 **500 行**（超限 400 `BATCH_LIMIT_EXCEEDED`）；导入一次一个文件、不可碎片化，逐行记且不设上限。
- 头行与明细的**行序不保证**：导入路径要求「有行必有痕」，明细紧跟各自业务行（`classification_service` 内部自带 commit），头行在批次收尾时写——读日志时按 `request_id` 或 `after.ids_hash` 归并，不要依赖 id 顺序。

### D4 受控枚举 + 契约表为唯一真源

`audit_contract.py` 定义 `ENTITY` / `ACTION` / `REASON`，`make_change()` 未知值抛 `ValueError`（开发期即炸）；同一模块持 `EndpointRule(method, path, entity, action|EXEMPT, status, 理由, 登记日期)` 表，`status ∈ traced|planned|exempt`——`planned` 即剩余工作量，可枚举、可递减。

### D5 快照分型

`create` → `after` 关键字段全集、`before=null`；`update`/`correct` → **仅变更字段**；`delete` → `before` 关键字段全集、`after=null`。理由：取证问的是「哪个字段从多少变成多少」，全列快照把噪声塞满 diff。

### D6 脱敏做在单点

`audit_service` 内对**凭证类键名**自动替换为 `"<redacted>"`，同层追加 `<key>_fp`（sha256 前 8 位）与 `<key>_len`（原值长度）；**入参不被就地修改**；`make_change` 与写库路径各跑一次（幂等）。新表新字段默认安全，不靠调用方自觉。

> **修订（2026-11-07，实现时）**：不以任意子串匹配，改为「整名 / `<模式>_` 前缀 / `_<模式>` 后缀」三段匹配，模式集 = `api_key|apikey|access_key|private_key|secret|password|passwd|token|authorization|credential`，其中 `token`/`authorization` 不做前缀匹配。**裸 `key` 刻意不进黑名单**：本域里 `vocab_key`、`idempotency_key`、`dedupe_key`、`max_tokens`、`token_count` 全是必须可读的业务/计量字段，脱敏它们不泄密、只毁取证。代价是形如 `authorizationHeader` 的非常规拼写不被识别——该类字段不进审计载荷，已由实现测试钉住。

### D7 理由（reason）只对纠正类「应该有」

`correct`/`delete`/`archive`/`owner_change`/`classification_change`/`restore` 属纠正类；枚举沿用 ADR-0026 词表（`correction|evolution|normalization`）+ `import|migration|other`；`reason_note` ≤200 可空；**存量行 NULL 不倒填**（语义＝未记录原因）。**理由是人声明的裁决，故系统上下文写入者（迁移、重建脚本、恢复后补记）不落 reason**——`record_sqlite()` 因此不接受该参数，系统动作的「为什么」由 `action` 与 `after` 自证。

**修订（2026-11-08，D7-a）**：强制口径由「运行时零强制 + `KNOWN_DEBT` 债务清单」改为 **owner 侧强制、system 侧放行**：

- 强制点在 `record()`（不是 `make_change()`——那里拿不到 actor）：`actor='owner'` ∧ `action ∈ REASON_REQUIRED_ACTIONS` ∧ 缺 `reason` → **422 `AUDIT_REASON_REQUIRED`**，业务与审计同事务回滚。
- `actor='system'` 一律放行（迁移、恢复、重建、调度器、advisor 自动链），否则系统路径会被自己的守卫锁死。
- **改身份不伪造理由**：确实由系统触发的动作（备份保留策略清理、目标激活时的隐式旧版归档）记 `actor='system'` + `reason='normalization'` + `after.source` 标明触发源（`retention`／`activation`），不冒充「我」的裁决。
- 前提是界面先有理由入口：12 个端点加可选 `reason`/`reason_note` query，前端四组入口（告警规则、字典 5 页、凭证单条+批量、目标归档）复用同一个理由输入组件；422 在前端转成可读提示且不关窗、不丢已填内容。
- `KNOWN_DEBT` 清零后即删除该集合与对应测试分支，改为「owner 侧纠正类审计行不得缺 reason」的正向断言。
- 上游 spec：`.scratch/audit-reason-enforce/spec.md`（E1–E8）；前置两批：`.scratch/audit-reason-capture/spec.md`（可选通道）、`audit_contract.py` 契约表。

### D8 链口径不动

`sha256.v1` 的 `FIELDS`（`occurred_at/actor/entity/action/row_id/before_json/after_json/evidence_ref/request_id/idempotency_key`）、算法、GENESIS、封存结构一字不改。`reason`/`reason_note` 是表列但**不进 FIELDS** ⇒ 改内容不改口径，不破链、不需重算、不需跨实现协调。

### D9 守卫＝路由枚举 × 契约表双向相等

测试枚举 `app.routes` 的全部写方法，断言「未登记的路由」与「已登记但已不存在的路由」两个集合都为空。运行期可选 warning，测试期必须 fail。

## 3. 后果

**正面**

- 「该不该留痕」从心证变成可套用的规则；新端点漏写会在测试里立刻变红。
- 密钥类字段默认脱敏，`llm_providers` 轮换可留痕而无需担心明文入库。
- 取证面能按 entity/action 枚举做筛选与文案；审计行带 reason 后能回答「为什么改」。

**代价与已知边界**

- 批量写入的审计行数同比放大（131 端点全留痕后，重度场景 5 年约 100 MiB，票 05 已量化）；单次超 500 行的批被拒，需要走「先导出再清空」流程。
- 脱敏不可逆：需要的排障信息（密钥前 8 位哈希、长度）之外取不回原文——这是有意的。
- `planned` 状态是**承认的债务**，不是完成态；它会在契约表里一直可见，直到清零。
- 链**仍不能阻止**有库写权限者重算全链并改写封存与 manifest（ADR-0013 边界不变）；对外文案一律「能发现不一致」，禁「不可篡改」。
- 恢复/换库类动作的审计行必须写进**替换后的新库**（替换会带走旧库的审计行），因此它是新库历史的第一条业务行——这一时序约束从本 ADR 起成立。

## 4. 被否方案

| 方案 | 否决理由 |
|---|---|
| 保持自由字符串 entity/action | 无法枚举、无法校验、筛选器无下拉；54 处调用点里只有 2 个字面量，读代码才知道有什么值 |
| 用 DB 触发器兜底留痕 | SQLite 单连接、触发器拿不到 actor 与业务语义，只会产出「有行无义」的记录，并与 append-only 的 ABORT 触发器打架 |
| 网关/代理层采集 | 无反向代理、无鉴权层，单一客户端，无「谁」可辨 |
| 装饰器登记写路由 | 要改 30+ 个生产签名，为守卫改生产代码不划算；路由枚举 + 契约表零侵入 |
| AST 扫描源码找 `record(` | 重构即误报，脆 |
| 把 reason 纳入 `row_hash` | 会逼全量重算与跨实现一致性协调，收益仅「改理由可被发现」，不值得动已冻结口径 |
| 无差别全列快照 | diff 噪声压倒信号，且体积翻倍 |
| 立即把 reason 转 API 必填 | 前端与 20+ 调用点无该字段，会立刻 500；改为 `KNOWN_DEBT` 显式债务 + 逐票清零 |

## 5. 与既有 ADR 的关系

- **ADR-0007**：本 ADR 不改「单点发射 / 同事务 / 失败阻断业务」，只补**判定口径**、**豁免登记**与**守卫**；ADR-0007 增一条修订行：「例外以 `backend/services/audit_contract.py` 的契约表为唯一来源」。
- **ADR-0013**：链口径与封存结构完全不动（见 D8）。`audit_head` 读回对账属票 03，本 ADR 不涉及。
- **ADR-0026**：`reason` 词表与「存量 NULL 不倒填」直接沿用，审计与名史共用一套语义。

# 编号迁移脚本与迁移前自动备份（弃 ad-hoc inspect，自建轻量 runner）

**状态**：已接受（2026-10-01，随 v5.0.0 落地）。

**背景**：v4 时代每次启动由 `db_migration_service.migrate_database()` 用 SQLAlchemy inspect 现场判断并跑全部结构变更：无版本记账、无执行史，且**迁移失败仅记日志、应用照常启动**（可能在半迁移库上跑业务）；备份为裸拷 `.db`（WAL 下非一致快照、不含凭证），任何结构变更前没有自动安全网。一期根基重构（实施策略裁决 §3 第 1~2 步）要求：备份先行、变更可追溯、失败必须可见。规格：`.scratch/v5-backup-fix/spec.md`、`.scratch/v5-migration/spec.md`；上游：`docs/design/system-architecture.md` §4、`docs/design/implementation-strategy.md`。

**决策**：

- 建立 `backend/migrations/NNNN_描述.py` 编号脚本目录（0001~0010 起步）：4 位编号单调递增、永不复用、允许空洞；每脚本暴露 `upgrade(conn)` 并**体内保留存在性守卫**（幂等，兜手动重跑与部分失败）；无 down 脚本＝**不支持降级**由机制明示。
- 自建 runner（`run_migrations() -> MigrationReport`）：`schema_version` 表（version/name/baseline/applied_at）由 runner 裸 SQL 自建、不入 models/create_all；按文件名动态发现（importlib，**文件名即真相、无注册表**）；每脚本一个事务，成功即登记；任一失败 → 回滚该脚本 → **fail-fast 中止启动**（日志含失败编号＋前置备份路径），修复后重启自动从首个未登记编号续跑。
- **迁移前自动备份**：仅「有既有业务数据且存在待执行脚本」时调步骤 1 的 `create_backup(reason="pre_migration", prune=False)` 产 zip bundle（manifest＋在线一致快照＋凭证）；备份失败＝中止迁移（宁可不起，不裸迁）。
- **基线认领**：v4 老库首跑把 `CLAIM=True` 标记的存量编目（0001~0007＝旧 inspect 机制每启动必跑、行为已收敛）登记 baseline=1 而不重复执行；v5 新增脚本（0008+，无标记）即便首跑也实际执行——认领机制不会吞掉新迁移。
- seed（来源组 / LLM 供应商）不入编号：保持每次启动幂等运行、吞异常仅 warning 的现状语义。

**Considered Options**：

- Alembic → 弃：单用户单机 SQLite、stdlib 优先，Alembic 的 env 栈与 autogenerate 在本项目规模下是额外维护面；自建 runner 约 200 行即可满足编号/事务/续跑/记账，且 fail-fast 与备份钩子完全可控。
- 保留旧 inspect 机制仅加记账表 → 弃：无编号史就无法表达「哪个变更跑过、从哪续跑」，每次启动全量 inspect 的隐性回归面（v4 的 side 回填每次全表扫）正是认领机制要终结的。
- 迁移失败照常启动（旧行为）→ 弃：半迁移库上跑业务把故障面扩大到数据层；fail-fast 是有意收紧，环境性问题（如备份目录不可写）直接可见。

**Consequences**：

- 启动链固定为 `create_all → run_migrations() → seed`（main.py lifespan）；结构变更＝新增一个编号脚本，runner 零改动（步骤 3 的 0008 即首个实战样例）。
- 每次增量迁移在 `data/backup/` 留一个 pre_migration bundle：回滚＝git revert ＋ bundle 整库恢复（残留新表对旧代码无害）。
- fail-fast 意味着迁移脚本写坏会拒绝启动——换来的是「绝不在半迁移库上跑业务」；脚本幂等守卫要求每个新脚本自带存在性检查（约定进 code review 面）。
- `schema_version` 与 bundle manifest `generation` 世代位（v5 起填 5）共同构成「库在哪一代、怎么到那儿」的最小可审计事实。

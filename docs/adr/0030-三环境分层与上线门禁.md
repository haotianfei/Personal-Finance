# ADR-0030：三环境分层与上线门禁

**状态**：**已生效**（2026-11-09 业主冻结；原话「一起冻结 + 补 ADR 0030（推荐）」「三环境全部重排（含改 prod）」）
**上游**：`.scratch/env-tiers/spec.md`（L2，2026-11-09 冻结）、`.scratch/env-tiers/map.md`（决策 Q1–Q8）、`.scratch/db-dev-suffix/spec.md`（库角色四档，已冻结）
**下游**：`deploy/docker-compose.staging.yml`、`scripts/staging.sh`、`scripts/staging-refresh.sh`、`scripts/dev-up.sh|dev-down.sh|dev-status.sh`、`scripts/ci.sh`、`scripts/install-git-hooks.sh`、`deploy/scripts/release.sh|rollback.sh|prune-images.sh|backup-data.sh|install-backup-timer.sh`、`scripts/restore_drill.sh`、`docs/runbook-release.md`
**性质**：**可回退**（无表结构变更；回退＝停止使用 staging/门禁脚本，把生产恢复为手工 `deploy.sh`，端口改回 `deploy/.env` 两行）

## 1. 问题

改造前只有两档环境：开发根 `docker-compose.yml`（源码挂载）与生产 `deploy/`（项目 `person_fin`）。由此产生三个具体危害：

1. **上线没有预演面**：想验证一次迁移或一次构建，只能直接在生产的唯一一套容器上做，唯一的验证手段是上线后的 `smoke.sh` 六条 curl。
2. **上线没有可回退点**：镜像只有 `:local` 一个可部署 tag，`deploy.sh` 就是 `up -d --build`。升级即覆盖，回退靠人记得上一次的 image id 再手工 `docker tag`——单用户系统里，出问题的那一次往往就是没人记得的那一次。
3. **门禁靠人记得**：`pytest`、`tsc`、文档锚点、公开安全扫描都存在，但没有任何一个入口把它们串起来，上线前的执行状态取决于当时那个人有没有想起。

此外，端口层面存在一个隐藏硬约束：`6665–6669` 属 WHATWG 屏蔽端口段，`next dev -p 6666` 直接报 `Bad port: "6666" is reserved for ircu`，浏览器也拒绝访问——旧 dev 端口在物理上不可用。

## 2. 决策

### D1 三档环境，编排文件各自独立

dev 用根 `docker-compose.yml`（源码挂载、热更新）；staging 用新增 `deploy/docker-compose.staging.yml`（项目 `person_fin_staging`，复用同一批镜像）；生产 `deploy/docker-compose.yml` 一字不动。

**否决「单文件 + profiles」**：生产编排文件一旦被参数化，任何一次误带变量的 `up` 都可能打到生产。宁可三份文件里有重复内容（重复只增加维护成本，误触会增加事故概率）。

### D2 端口全排：后端尾 8 / 前端尾 9，十位数字表环境

dev `6679/6678`、staging `6689/6688`、prod `6699/6698`。

**否决「只改 dev」**：一处不改就留下两套口径，runbook、README、scripts、MEMORY 会长期各说各话——本次正是在做这件事本身时发现旧值散落在六处。也否决继续用 `666x`（屏蔽段）与 `678x`（与生产现役唯一端口绑死，切不动）。

### D3 数据：staging 只吃生产库的**副本**，生产库只读

`scripts/staging-refresh.sh` 委托 `scripts/sync_deploy_db.py` 走 SQLite backup API（只读源库）取快照，落 `deploy-staging/data/`；默认 dry-run，`--apply` 才落盘；带白名单守卫与 `assets`/active 行数对拍。

**否决「staging 用合成数据」**：预演的价值在于数据形状真实（2600+ 行、真实分类树、真实审计链）。也否决裸 `cp`：生产库常带未合并 `-wal`，裸拷得到的是陈旧或不一致快照。

### D4 镜像：版本化 tag + `:local` 双写，staging 用专用 tag

上线同时打 `:<YYYYMMDD>-<shortsha>` 与 `:local`；staging 用 `staging-YYYYMMDD`。

**否决「staging 复用 `:local`」**：`up` 一旦静默回落 `:local`，staging 与生产就共享同一个 tag，生产的「当前版本」失去唯一性——这正是回退点能成立的前提。

### D5 上线只走 `release.sh`，七步内建回退点与自动回滚

`ci.sh` → 打 `rollback-<YYYYMMDD-HHMMSS>` 回滚点 → 构建双 tag → `up -d`（先写台账占位行）→ healthy + smoke → `RELEASES.md` 留痕 → ④ 之后任一步失败自动 `rollback.sh` 并把该行标 FAIL。默认 dry-run，`--apply` 才动生产。

**否决「继续手工 `deploy.sh`」**：手工流程的关键步骤（打回滚点、留台账、失败回滚）恰好是压力下最容易跳过的那几步；把它们放进脚本，才不需要在压力下有纪律。

### D6 门禁单入口 `scripts/ci.sh` + pre-push hook

默认档跑全量（pytest 全量 + tsc + next lint + 文档锚点 + 公开安全），`--fast` 跑契约子集，`--with-probe` 追加真浏览器探针；退出码 `0/1/2` 全仓统一。

**否决托管 CI**：仓库无 git 远端（单机、单人、文件同步），托管 CI 无处可挂。也否决「各脚本各自为政」：门禁的价值在于「有没有跑」这个二值信号，多入口等于没有信号。

### D7 staging 接受生产密钥，不禁出网

库副本自带 `provider_config.api_key`，原样使用。

**否决「清空密钥」与「`internal` 网络禁出网」**：预发的意义就是能跑真实识别链路；清空密钥后 staging 只能验证与 OCR/LLM 无关的路径，恰好放过了上线风险最高的一段。代价已记录：staging 持有一把可用钥匙，进程内调度器可真实消费。

### D8 备份：宿主整目录 tar + 保留策略 + systemd user timer；恢复演练独立项目

日备份留 14 天，每月 1 号那份额外留 6 个月（年龄取文件名时间戳）；`person-fin-backup.timer` 每日 03:00（`Persistent=true`，`--apply` 才写 unit）。演练用独立项目 `person_fin_drill` + 独立端口与网络，结束无条件清理。

**否决「演练进 CI」**：演练要解包数百 MB、起容器、校验审计链，成本与隔离要求都不属于每次 push 该做的事。也否决「cron」：用户级 systemd 可 `list-timers` 观测，失败有 journal。

## 3. 后果

- **好处**：上线有预演面（staging 跑同一批镜像 + 生产库副本）；升级前必有可回退点；失败自动回退；门禁只有一个入口且被 pre-push 复用；三处文档（runbook/README/MEMORY）与脚本共用一张端口表。
- **代价**：三份编排文件与三套数据目录需要同步维护；`ci.sh` 默认档约 15 分钟（pytest 全量 800+ 秒为主因），因此保留 `--fast`；staging 持有生产密钥与真实付费调用能力（D7）；恢复演练的报告目录会持续增长（按季度手工触发，不进自动流程）。
- **不可逆部分**：无。端口切换可由 `deploy/.env` 两行回退；脚本可停用；staging 项目可 `down` 后删除数据目录。
- **已知欠账**（登记在 `TODO.md` 与 spec §3）：生产端口切换、真实发布一次、失败自动回滚演练、`prune-images.sh --apply`、备份 timer 安装、恢复演练首跑——六项脚本就绪、待授权窗口执行。

# ADR-0016：当前值可就地修改，但修改仍是追加

**状态**：已接受（2026-10-30，业主拍板「界面像直接改，底层仍追加」）。规格：`.scratch/current-value/spec.md`。
**上游**：`CONTEXT.md`（「更正」「当前值」「沿用值」）、ADR-0001（扁平快照）、ADR-0007（append-only）、ADR-0013（hash-chain）、ADR-0015（零额合法）；`.scratch/asset-atomic/design.md` §7.3（本次推翻其交互结论）。
**下游**：`backend/services/asset_service.py`（当前值读模型与写入 helper）、`backend/routers/assets.py`、`frontend/src/app/records/page.tsx`；`docs/design/database-map.md`（不变量表）。

## 1. 背景与问题

`assets` 是全量流水式账本，界面只有一种呈现：所有记录按日期平铺在 `/records` 表格里。想修订某个资产的金额，需要先在流水中定位那一行、打开编辑弹窗、保存时前端再拆成三个请求（属性 / 更正 / 改名），且已录金额本身不可覆盖，只能走「更正」。

后果是日常操作成本过高：「看一眼当前值、顺手改一个数」这一财富管理最频繁的动作，被迫走审计级的更正流程。用户在 2026-10-30 提出：应当有「每个资产一行、显示最新值、就地可改」的视图。

关键事实（此前被误解，特此记录）：

1. **限制不在哈希链上**。`assets` 表**无触发器、无哈希列**；hash-chain 位于 `audit_log`（ADR-0013），与快照表无关。
2. write-once 是**应用层策略**：`asset_service.py` 对 `asset_name/amount/asset_date/side` 抛 `WriteOnceConflict`，路由转 409；金额唯一写入通路是 `correct`（同日追加 + `superseded_by`），且**强制复用原记录日期，不能移动日期**。
3. 部分唯一索引 `uq_assets_item_date_active`（`asset_item_id, asset_date` WHERE `superseded_by IS NULL`）保证「同项同日仅一条有效行」。
4. 已存在同类雏形 `CopyFromLastPanel`，但只处理「未录入」行，已录行不可改。

## 2. 决策

**D1 只改交互层，不改存储语义**：新增派生读模型**当前值**（每个资产项截至某参考日的最新有效记录），并在其上提供金额就地编辑。界面表现为直接修改，底层仍全部经 `create` 或 `correct` 追加。**不引入物理 UPDATE**。

**D2 当前值不是实体、不落库**：它是「沿用值」在单项粒度的投影，纯读端派生。因此不违背 ADR-0001「不拆 Holding / Valuation 两实体」的结论。

**D3 编辑映射为「默认记一次新估值，冲突自动转更正」**：输入框默认在参考日新建一条记录（语义：我现在重新估了一次）；若该资产在参考日已有有效行，则自动转为更正（数改、日期不变），**不弹窗、不报 409**。历史日期视图（as-of）中的编辑只能更正已有值。

**D4 写入口收敛**：新增端点 `PUT /api/assets/current/{item_id}`，分支判定在**单一服务 helper** 内完成，路由不得散写；幂等键与审计动作名复用现有机制。

**D5 编辑面收窄**：只有每个资产项的**最新**有效记录可就地修改。历史行只能进入明细走更正。`side` 在当前值表只读 —— 改方向是账本事实变更，须显式更正。

**D6 必须有陈旧度**：每行强制显示估值日与距今天数；超过 30 天给弱提示。理由：库内 132 个资产项中 96 项的最新记录停在同一天（约 40 天前），单行视图不标日期会让「当前值」被误读为当期实测。

**D7 撤销走既有端点**：新增则删除该行，更正则更正回原值，均写审计。不新增后端撤销接口。

**D8 批量重估不进入当前值表**：月度批量仍由 `CopyFromLastPanel` 承担，避免出现第三套录入流程（延续 `asset-atomic/design.md` §7.4 的结论）。

## 3. Considered Options

- **允许对最新行物理 UPDATE**（最直观的「直接改」）→ 弃：需推翻「更正」定义与 as-of 口径、改写 `database-map.md` 的不变量、为 `assets` 补触发器，还要为历史重写建立单独备份与回滚流程（db-audit 已就此警告）；而收益仅是省一次追加，代价与不可回溯风险不成比例。
- **新建 Holding / Valuation 实体承载「当前持仓」** → 弃：ADR-0001 已判定为过度设计；本需求只需读模型，拆实体会让「快照」与「持仓」互为第二真源。
- **保留流水账，只优化编辑弹窗** → 弃：用户的问题不是弹窗难用，而是没有「每项一行」的视角；优化弹窗无法解决定位成本。
- **当前值表内提供「沿用此值录入今日」快捷按钮** → 暂弃：该动作批量才有意义，而批量正是 `CopyFromLastPanel` 的职责；先观察一轮月度流程再议，避免录入路径增殖。
- **把当前值做成独立路由 `/assets`**（asset-atomic D1 的正式形态）→ 暂缓：本期在 `/records` 内以 tab 落地，改动面小、可快速验证；资产项目录与时间线仍留在 asset-atomic 规划中。

## 4. Consequences

- 每次编辑产生一行历史 + 一条审计；`assets` 行数随编辑频次增长（当前 4193 行，量级无虞）。`superseded_by` 链因此成为「编辑史」，明细页须能渲染被更正的旧行（现有 `include_superseded` 已支持）。
- 即时保存 + 默认新估值意味着误输入会立即落库，故 D7 的撤销是必要条件而非附加功能。
- `assets` 仍无触发器兜底，「应用层是唯一防线」的面积因新增写入口而扩大；D4 的单一 helper 是控制该风险的手段。
- 当前值读模型与占比/分析口径必须同源（按 `asset_item_id` 分组），否则改名后两个页面给出不同数字；本期同步修正 `proportion_service` 的按名分组。
- `.scratch/asset-atomic/design.md` §7.3 的「已录行显示当前值与「更正」而不是可覆盖输入」在交互层被本 ADR 取代，其存储结论（追加不覆盖）保留。
- 回滚＝撤下前端 tab 与两个端点，账本数据无需迁移。

**上游**：`.scratch/evidence-manager/spec.md` D7（L2，2026-11-05 冻结）；`docs/design/business-architecture.md:105` R-12（该字段的原始设计意图）；`backend/models.py:888` 注释「对账锚点（投顾总金额）」
**下游**：迁移 `backend/migrations/0030_drop_evidence_anchor.py`（`screenshot_evidence` 12 步重建）；`backend/models.py`、`backend/schemas.py`、`backend/routers/screenshots.py`、`backend/services/screenshot_service.py`、`backend/scripts/{screenshot_cli,screenshot_spike}.py`、`scripts/rebuild/{s2_plan_clean,s4_rebuild_db}.py`、`frontend/src/{types/index.ts,app/screenshot/page.tsx}`、`docs/design/database-map.md`

## 1. 决策

删除 `screenshot_evidence.anchor_amount` 列，并清理全部读写点（spec §1.4 的 22 处 + 重建管道两处导出/落库列）。

## 2. 现状证据（复核于 2026-11-05）

- **设计意图存在**：R-12 设想用「截图上的汇总金额」当对账锚点，与系统合计比对。
- **提取从未通用化**：`backend/services/screenshot_service.py:1461` 硬编码判断单一 App 文案「投顾总金额」；通用标签集 `_TOTAL_LABELS`（`:893`）只被 `_is_total_label` 用于**排除**汇总行（`:994/1036/1124/1145`），从未用于提取锚点。
- **实测量级**：运行库 `deploy/data/person_fin.db` 只读计数——`screenshot_evidence` **29 条**，`anchor_amount IS NOT NULL` **1 条**。
- **无比对逻辑**：`docs/design/gap-inventory-backend.md:37` 已记录「仅落存与回显，无差异比对端点｜部分」。前端只当数字显示（`app/screenshot/page.tsx:985` 单图、`:2836-2852` 批次合计），无判定。
- **无消费方**：全仓无任何代码读取该值参与计算、报警或导出决策。

## 3. 理由（业主裁决，2026-11-05）

**差额不可解释。** 截图上的总额常包含「预计可借」「昨日收益」「已赎回仍展示」等**有意排除**项，因此「系统合计 − 截图总额」的差值无法区分两种截然不同的原因：

1. 解析漏读了某一行（真缺陷，应报警）；
2. 截图上那一项本就被主动剔除（正常，不应报警）。

两者的差值长得一模一样。一个无法区分「错」与「对」的报警条件，会持续制造假阳性和假阴性，最终被人关掉——那么它带来的只是维护成本与「我们在对账」的错觉。**字段因此无法承担 R-12 赋予它的职责，删除优于留着考据。**

补充理由：人工确认录入后金额已被人校验过，锚点作为第二道防线是冗余的。

## 4. 否决的替代方案

1. **保留列只删显示。** 否决：留一个永远为空的列，下一代读到会重新花时间考据它为什么在（并可能误以为有代码在维护它）。业主明确要求「纯净」。
2. **补齐提取逻辑，覆盖更多 App 文案并做报警。** 否决：条款 3 的根因（差额不可解释）不因提取更全而消失；扩文案只降低第 1 类漏读，无法消除第 2 类的正常差额。
3. **降级为「来源汇总金额」纯存证字段（不比对）。** 否决：截图原图已经完整存证（`data/evidence/` + SHA256），把图上的一个数字再抄一份进库，既不增加可追溯性，又制造一个新的、无人读的字段。
4. **迁移为通用 `source_summary_amount` 并接入对账 UI。** 否决：与 3 同因——没有可判定的口径，UI 只能把两个数字并排显示，让用户自己猜哪个对。真要做对账，前置条件是「逐项映射到账本行」，那是另一个特性。

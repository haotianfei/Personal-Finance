# ADR-0022：凭证文件名由服务端生成，原图信息存入独立 `image_meta` 列

**状态**：**已接受（2026-11-05，业主签字，随 `.scratch/evidence-naming/spec.md` L2 冻结）**
**上游**：业主 2026-11-05「凭证命名需要建立一套规范」「原始图片的信息，最好有一个字段可以保留下来，如 exif、名称等等」；`.scratch/evidence-manager/spec.md`（凭证管理的既有边界）
**下游**：迁移 `backend/migrations/0032_add_evidence_image_meta_and_recognition.py`；`backend/services/screenshot_service.py:1698-1753`（命名与元数据写入）；`backend/scripts/rename_evidence_files.py`（存量改名）；`backend/requirements.txt`；`docs/design/database-map.md`；`CONTEXT.md`
**性质**：**新增列（可回退）＋ 命名规范（约束今后所有新凭证）**；不是不可回退决策，故否决方案与代价一并记录，避免日后重新争论。

## 1. 决策

1. **文件名由服务端计算**，格式 `<上传时刻 YYYYMMDD-HHMMSS>_sg<source_group_id>_<sha256 前 12>.<ext>`，目录仍 `<上传年>/<月>/`。客户端原始文件名**不再进入文件路径**；命名基座只用不可变字段（上传时刻 + `source_group_id` 自增主键 + 内容哈希）。
2. **新增 `screenshot_evidence.image_meta` TEXT（JSON，可空）**，存白名单字段：`width/height/bytes/format` + EXIF 子集 `DateTimeOriginal/Make/Model/Software/Orientation`。**不存 GPS**。
3. `original_filename` 语义不变（客户端原名原样保留，含历史脏名）。
4. 存量 28 条按新规则一次性改名（独立脚本 `--dry-run` / `--apply`，前置备份；**不放迁移**）。
5. `pillow` 显式写进 `requirements.txt`（当前为传递依赖）。

## 2. 现状证据（复核于 2026-11-05）

- 命名实现：`backend/services/screenshot_service.py:1723-1728`——`stem` 与 `ext` 直接取自客户端 `file.filename`，仅做字符消毒。
- 运行库 `deploy/data/person_fin.db` 只读计数（28 条）：**23 条** `original_filename` 形如 `shot_upload_<8 位随机>.jpg`，正是服务端 `tempfile.mkstemp(prefix="shot_upload_")` 的临时名；仅 **5 条**是真实手机截图名（`Screenshot_<日期>_<时间>_<包名>.jpg`）。
- 全库无任何列记录图像尺寸、拍摄时间、设备或软件；`image_meta` 之下的空档意味着无法回答「库里这张是不是原图」。
- `backend/requirements.txt` 无 pillow；容器内 PIL 13.0.0 与本机 12.3.0 均为传递依赖。

## 3. 理由

**文件名继承客户端名 = 路径由外部决定。** 客户端（浏览器、脚本、旧上传路径）传什么，服务端就把它消毒后写进磁盘路径。后果已经发生：23/28 的凭证文件名是临时名，既不可读也无法与来源对应。一次性的消毒只能挡住路径穿越，挡不住"名字无意义"。

**可读性需要的是三元组：什么时候传的 / 哪个来源组 / 哪一张。** 客户端原名只偶尔携带其中一项（手机截图名带日期），而服务端三样都确定知道：上传时刻、来源组主键、`file_sha256`。把它写进名字，等于把服务端已知的事实外化成可检索的路径。

**原始信息必须进字段，而不是靠文件名承载。** 业主的要求（"原始图片的信息，最好有一个字段可以保留下来"）与改名并不冲突：文件名负责**定位**，字段负责**溯源**。`original_filename` 已保存名称，缺的是像素与拍摄信息——这才需要新列。

**元数据存 JSON 而非多列。** EXIF 字段稀疏且随设备变化（手机截图往往只有 `DateTimeOriginal`，无 `Make/Model`），拆成 5 个几乎全 NULL 的列会持续招惹「为什么这列是空的」的追问；一条 JSON 加白名单，读侧按需取。

**改名不放迁移。** 文件移动不是数据库事务的一部分：迁移中途崩溃会留下"库里新名、磁盘旧名"的半截状态，而 SQLite 事务无法回滚 `os.replace`。脚本能打印 old→new 清单、能 `--dry-run`、能停在中途并逐个重试。

## 4. 否决方案

| 方案 | 否决理由 |
|---|---|
| 保留客户端原名（现状） | 23/28 已是临时名；名字质量取决于调用方，服务端无法收紧 |
| 文件名保留原名 + 加前缀（`YYYYMMDD_原名_sha12`） | 长度可达 100+ 字符，且仍把客户端名写进路径——根因未除 |
| 用 `slug` 做文件名（`YYYYMMDD_cmschina_sha12`） | **slug 可变**（业主 2026-11-05 裁决）。组改名后新旧文件命名口径分裂，同一组出现两种前缀，想核对「这组有哪些凭证」就不能靠文件名了 |
| 用来源组显示名做文件名 | 现有组名几乎全中文：ASCII 消毒后只剩下划线（信息量为零），写非 ASCII 又给打包/备份/跨平台留长期隐患 |
| 纯内容寻址（`sha/aa/bb/…` 分片） | 最干净，但人眼完全不可读；业主的需求恰是"从名字能看出东西" |
| 拆成 `width` / `height` / `camera_make` / `shot_at` 等多列 | 稀疏列爆炸，且每次厂商变化都要加列 |
| 全量 EXIF 入库（含 GPS、厂商私有 tag） | 位置信息无业务价值，且会把家庭住址级数据多留一份；私有 tag 语义不明 |
| 用 EXIF 拍摄时间做文件名时间戳 | 截图常常**没有** EXIF（23/28 的历史样本里就不保证有），缺值时要造一个假时间；上传时刻必然存在，且拍摄时间已由 `image_meta.exif.DateTimeOriginal` 单独留存 |
| 改名写进迁移 0032 | 文件移动不可事务化，失败即半截状态，无 dry-run 余地 |

## 5. 代价与影响

- `schema_version` 29 → 32（0032 加列；0030/0031 已于同批执行）。
- 28 条 `file_path` 一次性变更；文件名不再与 `original_filename` 前缀一致（这是**预期**，不是缺陷）。
- 新增直接依赖 `pillow`；镜像需重建。
- 名单外的历史脏名（`shot_upload_*`）成为永久痕迹：`original_filename` 不修正，只在路径层被替换。
- 组改名或改 slug **不影响**既有文件名（基座是 `source_group_id`），也不触发任何移动；查询以 `file_path` / `source_group_id` 为准。

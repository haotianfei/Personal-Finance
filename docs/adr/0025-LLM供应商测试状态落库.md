**性质**：**新增可空列（可回退）**，但「测试结论属于供应商实体，还是只属于当下这一屏」是一次性取向决策，故记录。

## 1. 决策

1. **在 `llm_providers` 上新增四个可空列**：`last_tested_at`(DateTime) / `last_test_ok`(Boolean) / `last_test_message`(String(300)) / `last_test_elapsed_ms`(Integer)，只保存**最近一次**测试的结论。
2. **四列全部可空且不设默认值**。`NULL` ＝ 从未测试，`false` ＝ 测过且失败——这两件事必须能分开。给 `last_test_ok` 设 `default=False` 会把「没测过」说成「测过但失败」，是这个决策最容易犯的错。
3. **写入只发生在 `POST /api/llm-providers/{id}/test` 内部**，且**对外响应形状不变**，仍是 `{ok, message, elapsed_ms}` 三键。查询侧靠列表序列化的增量字段，不新增端点。
4. **配置变更即作废旧结论**：`base_url` / `model` / `api_key` 的值**实际改变**时清空四列；`label` / `sort_order` / `enabled` / `is_default` 的变更不清空。判定用「新值 != 旧值」，不用「字段是否出现在 payload 里」——编辑表单回传全量字段，按后者判断会让「改个名字」误清结论。
5. **`api_key` 传空串不算变更**：沿用既有的「留空＝不改 key」语义，既不清空结论也不报错。
6. **展示形态是行内三态徽章 + 保留原有 toast**。徽章承常驻可扫，toast 承「我刚点完」的即时反馈，两者职责不同，不互相替代。

## 2. 否决的方案

| 方案 | 否决理由 |
|---|---|
| 前端 `localStorage` 记住上次结果 | 换浏览器或清缓存即丢；后端永远不知道某家供应商测没测过，审计与排障都拿不到；同一份事实存在两个真相源。 |
| 只放前端内存（会话内可见） | 等于现状加一个刷新就消失的展示，没解决「一闪而过」这个抱怨本身。 |
| 保留旧结论并标注「配置已变更」 | 要判断「是否变更」就得存配置指纹，为一条提示引入一套一致性负担；且提示本身仍要人去读，不如直接说「未测试」。 |
| 存测试历史表（每次测试一行 + 时间序） | 当前没有消费方（无成功率统计、无趋势图、无告警），多一张表就要多一套生命周期与清理策略；等真有需求再另起 ADR。 |
| 让 `test` 端点返回整行、前端据此更新 | 无谓扩张契约面：既有前端与既有测试都只认三键；增量字段走列表序列化已经足够。 |
| 把结论塞进 `enabled` 或 `is_default` 之类的既有布尔列 | 一列一义；把「可用性」与「启停」混在一起，任何一处读错都会静默改变供应商选择行为。 |

## 3. 代价

- 一次加列迁移，表宽 +4 列；老库升级后这四列全为 `NULL`（历史测试无从追溯，不伪造）。
- `update_provider` 多出一段「比较新旧值」的分支，不再是「有字段就赋值」那么直白。
- **结论会随配置漂移**：改了 `base_url`、`model` 或 key 之后，用户必须重测才会看到新结论，期间显示「未测试」。这是刻意的保守，不是缺陷。
- 四列都是易变事实，数据库备份/对比时会看到与供应商定义无关的抖动。

## 4. 后续义务

- `docs/design/database-map.md` 的 `llm_providers` 条目需补这四列；`CONTEXT.md` 补词条「测试结论」。
- **零默认的降级行为不因本篇改变**：截图 AI 一致性校验取不到默认供应商时仍降级为 `unverified`，投资建议 advisor 仍返回 409。是否要改这两处，属于另一个决策。
- 若将来要做测试历史、成功率或趋势，须另起 ADR，**不得**在现有四列上扩展语义（例如把它们改造成「累计计数」）。

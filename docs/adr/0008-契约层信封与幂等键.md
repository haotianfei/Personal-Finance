# 契约层：统一错误信封、Idempotency-Key 幂等键、口径元数据 meta

**状态**：已接受（2026-10-01，随 v5.0.0 落地；本 ADR 即契约冻结的决策记录，形状单源为 `.scratch/v5-contract/spec.md`）。

**背景**：前后端错误面此前是 176 处 `HTTPException(detail=字符串)` 各写各的，前端 `api.ts` 把对象 detail 序列化成字符串——业务码与结构全部丢失，页面只能弹文案；无任何幂等机制（超时后「勿连续重试」靠口头劝阻）；计算类读响应无口径标注（哪天的快照、零值是「没有」还是「为 0」不可分辨）。步骤 3 的 409/冲突显式化已依赖结构化错误载荷。规格：`.scratch/v5-contract/spec.md`；上游：`docs/design/system-architecture.md` §6、`.scratch/v5-audit/spec.md` §8、`.scratch/v5-identity/spec.md` §5。

**决策**：

- **错误信封**：全部非 2xx 统一 `{"error":{"code","message","details"}}`，HTTP 状态码保留语义；错误码枚举集中 `backend/errors.py`（通用 4 + ledger 5 + ingest/backup 4 + 幂等 1，兜底 `GENERIC_<status>`）。main 注册四个 handler：ApiError→信封、RequestValidationError→`VALIDATION_ERROR`＋`details.fields[{field,message}]`（loc 展平点路径）、**HTTPException 包装器**（存量不逐一改造：含 code 的 dict 透传、准信封精确映射、字符串按码表转码）、全局 Exception→`INTERNAL`（不泄栈）。新代码一律 `ApiError`，code 精度增量收敛。
- **幂等键**：请求头 `Idempotency-Key`，前端**每个用户动作生成一个 uuid**、失败重试复用同键（防双击仍是按钮层职责）。服务端 `idempotency_keys` 表（编号迁移 0010）：同键同体（body sha256）→ 逐字节重放首次响应（含原状态码）；同键异体 → 422 `IDEMPOTENCY_KEY_REUSED`；pending>60s 视为可重跑；done 7 天 TTL 日清（复用既有 scheduler）。实现＝`idempotency_guard(scope)` 路由级依赖注入（39 条写端点；GET 与纯查询 POST 不挂）＋薄捕获中间件仅对被标记请求回写响应。单用户不做并发锁。
- **与天然幂等的分工**：正确性兜底始终是天然幂等（部分唯一索引、`(template_id,period)` 唯一、冲突显式清单/409）；幂等层只提供重放安全与友好性。审计行带 `idempotency_key`（与 request_id 并列，语义不同：每请求 vs 每动作）。
- **口径元数据**：计算类读响应顶层 `meta = {snapshot_date, basis:{schema_generation:5, identity:'asset_item', principal:预留}, degradations:[{code,scope,message}]}`；降级枚举 `NO_DATA` / `DATA_MISSING_CARRY_FORWARD`（`RATE_UNAVAILABLE` 仅预留二期 TWR/XIRR 消费），宁缺勿滥、由计算过程收集；列表类响应不挂（无口径语义）。
- **世代与切换**：破坏性契约变更随数据世代（V5）一次到位，单客户端同 commit 窗口切换，不做 URL 版本化；备份 bundle `generation` 位填 5 作为收官标记。

**Considered Options**：

- 纯中间件实现幂等 → 弃：需路由级选择性（只覆盖写端点）且中间件看不见路由依赖标记；采「依赖判定＋中间件回写」分工，旁路语义集中在依赖内。
- 176 处存量逐一改抛 ApiError → 弃（本步）：包装器已保证「处处有信封」，全量手改波及面大且无新增信息；code 精度按增量收敛（新代码一律 ApiError）。
- 幂等键服务端自动生成 → 弃：去重语义属于「用户动作」，服务端无法区分重试与重复提交；客户端在动作发起点生成才能表达意图。
- meta 以 HTTP 响应头传输 → 弃：与 body 同源事实拆两处，前端缓存/react-query 场景下头易丢失；顶层字段自描述。
- 双形状兼容期（同时发 detail 与 error）→ 弃：单用户单客户端，同窗切换成本低于长期双写维护成本。

**Consequences**：

- 前端 `request()` 抛 `ApiError{code,status,message,details}`（message 保持人读，多数 toast 零改动）；4 处结构化适配：records（WRITE_ONCE_CONFLICT→更正引导、SNAPSHOT_CONFLICT→`details.conflict_records` 弹窗）、screenshot（apply 冲突清单展示＋每图持久键，超时重点击=同键回放防双写）、import（`skipped[]` 显式清单）、backup-restore（`warnings[]` 警示条＋信封错误解析）；漏网端点有旧 `detail` 回退兜底。
- 契约面冻结入步骤 5 清单：`/api/audit-log` 两端点、信封形状、`meta` 形状、`Idempotency-Key` 语义；后续变更（如三期 hash-chain、幂等 `idempotency_key` 列扩展）走新 ADR。
- multipart 端点幂等退化为「键＋scope」级去重（不读原始体，避免破坏 UploadFile 解析）——回放有效、异体检测失效，单用户可接受。
- 回滚：handler/中间件/api.ts 均可独立 revert；0010 新表与新列残留无害。

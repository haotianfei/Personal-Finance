# ADR-0029：汇总项与构成关系（叶子计量 / 构成边表 / 批次核对）

**状态**：**已生效**（2026-11-09 业主签字；上游 `.scratch/multi-page-aggregate/spec.md` 同日冻结）
**上游**：业主 2026-11-08 需求（转述）——多页录入场景下，主页的汇总项实际由其它页的两个子项构成，只需录入子项、汇总项仅用于金额核对；并询问上传时是否需区分子页与主页；同轮追加希望父子识别项支持拖动关联（子项拖到父项下，树形）

## 1. 问题

一张截图里的「贵金属」是汇总数，它的构成分散在另外几张截图（示例金产品A、示例金产品B）。今天的实现有两个缺口：

1. **汇总行无处安放**：`total_labels` 词表只把这类行**整行丢弃**（`backend/services/parser_rules.py:43-44` → `screenshot_service.py:1033`），行不进 preview，于是既不能核对、也不能解释「为什么这行没入账」。
2. **没有「构成」这个概念**：`lineage_links` 只有 `merge/split/revision`，语义是**接替**——写入后前身一律归档退出计量（`lineage_service.py:146-152`）。父子**同时存在**的关系无处表达；而净值是逐行相加、假设每项独立计入（`analysis_service.py:243-260`），父子一旦同在 active 就会立刻双计。

## 2. 决策

### D1 计量单元从构成关系**派生**，不在项上存布尔位

一个项只要在某条构成边里作为 `parent_item_id` 出现，就不计入计量口径（净值、占比、告警、导出合计）。子项照常计入。解除关系或子项清空后**自动恢复**，不留例外记录。

否决「在 `asset_items` 上放 `is_aggregate` 标记」：解除关系时忘清一次，该项就永久从净值消失，而界面上看不出异常——这是静默错账。

### D2 判断收口到单点谓词

并入 `backend/services/snapshot_identity.py` 的计量谓词（`proportion_service` 与 `_sum_as_of` 共用），形态为 `NOT EXISTS (item_compositions WHERE parent_item_id = ...)`。任何出口不得另写一套过滤，四出口一致性由 `test_total_consistency.py` 的登记表范式锁死。

### D3 构成用独立边表，一子一父、全额归属、无权重

`item_compositions(id, parent_item_id, child_item_id UNIQUE, created_at, note)`。一子一父（撞 `UNIQUE` → 409 `COMPOSITION_PARENT_CONFLICT`）；不允许比例分摊；允许多层但禁环（应用层祖先链 409 `COMPOSITION_CYCLE`，DB 加 `CHECK(parent_item_id <> child_item_id)`）。

不塞进 `lineage_links`：那张表的写入路径会归档前身，与「父子共存」直接冲突，混用会让同一张表有两种不相容的生命周期语义。

### D4 汇总行是**行级动作**，不是新取值域

apply 载荷新增与 `skipped` 同形的 `reconciles: [行号]`；`PreviewRow.action` 取值保持不变。体验上该行留在清单里可见、金额变灰、徽章为「核对」；写入侧**零副作用**（不写 `assets`、不改 `display_name`、不沉淀别名、不动血缘），并从 `zero_names`/`unrecognized` 候选里剔除（回执 `zero_skipped_due_to_reconcile`）。

### D5 批次是真实对象，`finalize` 是唯一校验点

`POST /api/screenshot-batches` 先建批次；各图 apply 带 `batch_id`（缺省时行为与今日逐字段一致）。`POST /api/screenshot-batches/{id}/finalize` 单事务完成：校验成员齐全（409 `BATCH_NOT_COMPLETE`）→ 逐条算差额 → 差额≠0 且无理由则 409 `RECONCILE_MISMATCH` → 写核对记录 + 建立/校验构成边 + 置 `finalized` + 一条审计。

允许 `partial`，**永不跨图回滚**：现有 apply 是逐图串行 + 每图独立幂等键，硬引入跨图事务会牵动整条基线，收益不抵风险。

### D6 差额零容差

只有三个合法出口：改子项、补子项、显式接受（理由必填，400 `RECONCILE_REASON_REQUIRED`）。不设精度容忍带，不生成吸收差额的分录。业界没有「静默接受非零差额」的先例；有差额就必须有人对差额负责。

### D7 归父两条路径并存

「归到…」选择器为主路径，行首手柄拖拽为加速器（拖到自身/后代/非汇总行均拒绝，Esc 回滚）。理由是 WCAG 2.2 2.5.7 要求拖拽必须有单指无拖拽替代（F108 明确：键盘等价不算满足），且 `aria-grabbed`/`aria-dropeffect` 已废弃无替代、APG 无拖拽模式。375px 下手柄消失，走工具条命令。

## 3. 否决的方案

| 方案 | 否决理由 |
|---|---|
| 父项存 `is_aggregate` 布尔位 | 解除关系忘清即永久漏计，且界面上看不出来 |
| 父项读时派生求和（父金额＝子项之和） | 改动面覆盖全部读路径；且父项历史快照与实时求和会打架 |
| 复用 `lineage_links` 表达构成 | 那张表写入即归档前身，与「父子共存」矛盾 |
| 一子多父 + 权重 | 金额要拆成份额，个人记账里解释不清 |
| 汇总行沿用 `total_labels` 整行丢弃 | 行不可见就没法核对，也无法解释「为什么这行没入账」 |
| 精度容忍带 / 自动吸收差额分录 | 金额全是两位小数，容忍带只会掩盖错抓；吸收分录会越滚越脏 |
| 只做拖拽不做选择器 | 不满足 WCAG 2.5.7；触屏拖拽事件不完整 |
| 跨图事务回滚 | 需重写逐图串行 apply，风险远大于收益 |

## 4. 代价

- **历史数据不修正**：父项既有快照保留原值、只退出计量；在修正之前，历史净值曲线上的父项段与子项段会并存（总额不受影响，因为只算叶子）。业主已明确「历史后面再想办法进行一次数据修正」，属图外事项。
- **两套「不计入」并存**：`total_labels`（不解析）与汇总行（解析但不入账）语义不同，文档与 UI 都必须写清，否则用户会问「为什么有的行消失了、有的行留着变灰」。
- **批次表引入新的生命周期**：`open/partial/finalized/abandoned`，需要一条清理弃置批次的路径（本期只允许置 `abandoned`，不做删除）。
- **总表改造**：复核页从「按图分表」改成「一张总表 + 图来源筛选」，是这次改动里唯一会让人「找不着原来位置」的地方。

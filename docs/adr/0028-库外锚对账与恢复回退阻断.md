---

## 1. 问题

ADR-0013 的审计链能回答「行有没有被改」，回答不了**「整个库是不是被换成了旧的」**：把库文件换成三天前的备份，链在那个版本内部是自洽的——每个 `prev_hash` 都对得上，`verify()` 返回 ok。

此前的唯一线索是备份 `manifest.json` 里的 `audit_head`，而它**只写不读**（`backup_service.py` 写、无人比对）。`ensure_chain()` 察觉 `audit_log.max_id < chain_state.last_id` 时也只 `logger.critical`，既不阻断也不报告。于是「我是不是把库恢复成了旧版本」这个问题，系统层面没有答案——只能人肉翻备份时间戳。

而恢复恰恰是最容易发生整库回退的动作：业主备份、试错、发现不对、恢复，其间任何一次选错包都会让三天的留痕静默消失。

## 2. 决策

### R1 对账时机：三处，各司其职

| 时机 | 动作 | 后果 |
|---|---|---|
| 启动后（`db_migration_service.ensure_chain` 之后） | `integrity_report()` 扫全部锚并比对 | 只 `logger.critical`，**绝不抛异常、绝不阻止启动** |
| 恢复替换前 | 用**目标包**的 `audit_head` 与当前库链头比对 | `db_older`/`diverged` → 409 `AUDIT_ROLLBACK_DETECTED`，需 `confirm_rollback=true` 越过 |
| 日封存后 | 封存把当日链头写入 `audit_chain_seals` | 封存行本身就是当日的库内锚，`lag` 由端点暴露 |

### R2 对账对象：全部锚，取最坏

`read_anchors()` 扫备份目录里的 `manifest*.json`，**也读 `*.zip` bundle 内嵌的 `manifest.json`**（本系统的生产备份形态就是 zip；只读散落 JSON 会让端点在真实部署里恒空）。每个锚产出 `match`/`db_newer`/`db_older`/`diverged`/`unknown`，`worst_status` 取严重度最高者。恢复路径只比**目标包**那一个锚——别处的旧备份与这次恢复无关。

### R3 启动不阻断，恢复硬阻断

单用户系统没有值班人：**启动失败＝人进不来＝告警没人看得见**，这比漏报更糟。因此启动期只记录，真相由只读端点 `GET /api/audit-log/integrity` 呈现。

恢复则相反：它是**人的动作**、有明确意图、有确认通道，且错过就不可逆（旧库被覆盖）。默认拒绝 + `confirm_rollback=true` 显式越过，代价是一行表单字段，收益是不让「选错包」静默生效。

### R4 五值判定，方向靠参数摆位

`compare(current, anchor)` 里 `current` 是**被判断方**、`anchor` 是**参照**：

- 端点视角：`current`＝当前库、`anchor`＝旧备份 → `db_newer` 正常（库比旧备份新）；
- 恢复视角：`current`＝目标包、`anchor`＝当前库 → `db_older` 即「目标更旧」＝回退。

判定顺序**先看 hash 是否相同**（相同即同一个库，行数差异只是统计口径），hash 不同才用行数分新旧；行数也相同＝`diverged`（同一长度上的另一条链，最典型的「回退后又写入若干行」）。`anchor.audit_head` 缺失 → `unknown`。

### R5 恢复留痕补充对账结论

`backup/restore` 的审计行 `after` 增加 `integrity`（判定值）与 `rollback_confirmed`（**真的越过了才算 true**，只是传了参数而目标不旧时为 false）。不新增列、不进链哈希（ADR-0027 D8 不变）。

### R6 封存落后量并入同一端点

`seals{last_seal_id, max_id, lag}` 与对账结论同端点返回。`lag>0` 是常态（当日尚未封存），**不告警**——把它做成告警只会训练人忽略告警。

## 3. 后果

**正面**

- 「库被换成旧版」从无人知晓变成启动即报、端点可查、恢复前可拒。
- 恢复动作自带对账结论，事后能回答「这次恢复是不是回退、谁确认的」。
- 零新表、零链口径改动：`FIELDS`、`row_hash`、`verify()` 一字未动。

**代价与边界**

- 恢复旧备份的常规操作多一步显式确认（`confirm_rollback=true`）——有意为之的摩擦。
- 无 manifest 的旧裸 `.db` 与 `/upload-db` 判定 `unknown` 放行：这类文件根本没锚可比，拒绝它们等于禁止应急路径。
- 对账只能发现**有锚可比**的回退：锚在备份目录里，若连备份目录一起被回退/清空，对账会退化为 `unknown`。要跨过这一层需要外部锚（异地/外部公证），属已明确排除的方向（地图 Out of scope）。
- 文案纪律不变：链与对账**能发现不一致**，不写「不可篡改」。

## 4. 被否方案

| 方案 | 否决理由 |
|---|---|
| 启动时发现回退就拒绝启动 | 单用户无值班，锁死门外连告警都看不见；且容器化部署会进入重启循环 |
| 恢复一律允许，只事后告警 | 覆盖不可逆，事后告警等于「通知你损失已经造成」 |
| 加 `epoch` 列标记库代际 | 需要迁移 + 全链带代际 + 判定规则重写，收益仅「回退可定位到哪一代」，不值得 |
| 把对账结果纳入链哈希 | 对账是库外事实（依赖备份目录），进哈希会让链不再自证 |
| 每次写入都比对一次锚 | 常态 100 行/日、每写一行扫一遍备份目录，成本与收益倒挂 |
| 只信 `chain_state.last_id` 与 `max_id` | 只能发现**尾部被截断**，发现不了「换成另一条同样长度的链」 |

## 5. 与既有 ADR 的关系

- **ADR-0013**：本 ADR 补它能力边界的缺口（整库回退），不改其任何口径；`audit_chain_seals` 的封存语义与结构不动。
- **ADR-0027**：恢复留痕新增的 `integrity`/`rollback_confirmed` 是 `after` 内容，不新增列、不进 `FIELDS`，与 D8 一致。
- **ADR-0007**：恢复失败（含被对账拒绝）不写业务审计行——被拒绝的恢复不是一次发生过的写入。

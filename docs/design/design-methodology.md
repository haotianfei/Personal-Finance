# 系统设计方法速查（本项目适用版）

> 用途：一张面向非专业设计者的地图——「设计一套系统要经过什么、每步用什么方法、本项目现在走到哪」。
> 关联：`business-architecture.md`（设计产物）、`docs/adr/`（决策记录）、根目录 `CONTEXT.md`（术语表）。

## 一、系统设计是一条「逐层翻译」链

把「想要什么」逐层翻译成「怎么做」：愿景 → 业务 → 模型 → 结构 → 实现 → 验证。每层有产出物，上一层的产出是下一层的输入。**不要跳层**——跳过业务与模型直接设计表结构，等于把「拍脑袋的假设」硬编码进代码，这是新手最常见的坑。

| 台阶 | 核心问题 | 产出物 | 常用方法 |
|---|---|---|---|
| 0 愿景 | 为谁、解决什么痛点 | 使命 / 画像 / 痛点清单 | 5 Whys、JTBD |
| 1 业务架构 | 业务由哪些域构成 | 域 / 子域图、能力、流程、规则、角色 | 业务能力地图、事件风暴、DDD 战略设计 |
| 2 领域模型 | 原子是什么、怎么运转 | 聚合根 / 实体 / 值对象 / 不变量 / 术语表 | DDD 战术设计、生命周期建模 |
| 3 系统架构 | 怎么切模块与边界、契约长什么样 | 上下文图、分层、接口契约、数据模型、数据流 | C4 模型、arc42、信息隐藏 |
| 4 技术架构 | 用什么实现 | 选型、部署、运维 | 权衡分析、快速原型（spike）、ADR |
| 5 验证与演进 | 怎么证明对了、怎么安全地改 | 验证计划、测试策略、迁移方案 | 走骨架、垂直切片、演进式架构 |

## 二、六条贯穿始终的最佳实践

1. **从为什么开始**——每个设计元素都能追溯到一条真实需求（见 `business-architecture.md` §8 追溯表）。
2. **先立公理与不变量**——写死「绝不允许发生什么」，再推导结构（见 SDP-1~4 与 §5 不变量）。
3. **统一语言**——一套术语表，人和机器用同一本词典（`CONTEXT.md`）。
4. **结构先于实现**——推迟技术决策；设计阶段不迁就现状代码（本项目原则：设计优先、实现可弃）。
5. **小步验证**——先走骨架、端到端跑通，再加宽加厚。
6. **决策留痕**——一次决策一页 ADR；不写下来就会被反复推翻重议。

## 三、本项目采用：轻量 DDD 主干 + 工具箱

**结论：主干 = 轻量 DDD（战略 + 战术）+ 契约驱动 + ADR + 够用就好文档；其余方法论按需取用，不搞全套仪式。**

理由：本系统本质是「一个资产的生命周期」——典型的领域建模问题，DDD 正好对口；项目已在用其要素（域 / 子域 / 聚合 / 术语表）。企业级全套（微服务、事件溯源、TOGAF、完整 C4 四层图）对单人自托管系统不划算——取「够用就好」（Just-Enough）原则。

| 层 | 轻量版采用 | 本项目现状 |
|---|---|---|
| 0 | 使命 + 痛点 + 追溯表 | 已完成 |
| 1 | DDD 战略设计（域 / 子域 / 能力 / 流程） | 已完成（v1.0 冻结） |
| 2 | DDD 战术（聚合根 / 不变量 / 生命周期） | 已冻结（v1.0：资产项聚合根＋关系层） |
| 3 | C4 只取两级（Context + Container）+ 接口契约先行 | 下一步：系统架构阶段 |
| 4 | ADR + spike / 原型 | ADR-0001~0005 已在用 |
| 5 | 走骨架 + 数据世代迁移 + 冻结契约 | 部分在用（V1~V4、验收脚本） |

第 3 层的第一步是**上下文边界**——把主域 / 子域映射成模块边界与接口契约。

## 四、资源清单（少而精）

- Eric Evans《领域驱动设计》——DDD 源头（先读前两部分即可）
- c4model.com（Simon Brown）——架构图不啰嗦的画法
- arc42.org——一份够用的架构文档骨架
- Michael Nygard「Documenting Architecture Decisions」——ADR 的出处
- John Ousterhout《软件设计哲学》——深模块与复杂度控制

## 五、角色分工

方法论是给「还没有专家直觉」的人修的台阶——专家也走这些路，只是走得快。本项目不要求人人会画全部图：**用户是裁决者**（使命、公理、目标、拍板项），推演由 agent 完成。对每份产出物只问两句：「可回溯到使命吗？我认吗？」——这是设计里最值钱的动作。

# 实施策略裁决（保留 vs 重写）——决策稿（2026-09-27）

> 状态：待用户确认。依据：系统架构 v1.0（冻结）＋业务架构 v1.1＋前后端事实层盘点。
> 版本约定：现有实现为 v4.x（数据世代 V4）；本裁决与新架构的落地自 v5.0.0 起（数据世代 V5；V4→V5 数据迁移属一期「身份层落地」）。

## 1. 总策略

整体判定为「**保留骨架、重构根基、按设计新建空白域**」：F1 截图管线、凭证链、金额恒正+side、校正缝、人裁决采纳等已与冻结设计对齐，是本项目最有价值的存量，全部保留；但身份层（asset_name 字符串 vs 持久资产项 ID）、写语义（可改写/静默覆盖 vs write-once+追加更正）、审计承载物、契约风格四项属根基性偏离，须在**一期最先重构**——因为二期本金口径、血缘、转移事件全部悬在身份层之上，晚改一天就多一天把新能力建在将退役的键上；advisor、B2、家庭视图为零实现域，无所谓保留，直接按冻结设计新建。不做推倒重写：现有前后端与设计的偏离集中在「根基四件套」，业务管线本身是资产而非负债。

## 3. 关键路径与顺序

一期内部顺序（每步都是下一步的安全网）：
1. **备份修复**——DB 在线备份+凭证目录同备；这是一切实操的前置，现状裸拷不满足追溯链完整性；
2. **迁移机制升级**——schema_version+编号脚本+迁移前自动备份；
3. **身份层落地**——asset_items 表、asset_name→ID 一次性数据迁移、快照挂 FK、显示名史；此后所有新功能禁止再以 asset_name 为键；
4. **审计日志表**——append-only，先覆盖身份迁移、采纳、更正三条写路径；
5. **契约层冻结**——错误信封+幂等键+口径元数据 spec，前后端同步切换（单客户端，一次到位）；
6. **ingest 微调**——存证前置、任务落库。模块目录重组**不作为一期门槛**，以导入边界测试锁定依赖方向即可。

## 4. 风险与取舍

- **身份迁移是全局最高风险动作**：一次脚本错可毁真实数据——故备份与迁移机制必须先于它，且迁移前做一次可恢复演练。
- **新老键双轨蔓延**：迁移窗口内若继续给 asset_name 加功能会加深债务——建议冻结存量 API 新增，只出不进。
- **契约切换为破坏性变更**：错误信封/幂等键需前后端同窗口上线，短期开发速度换取此后各期并行效率，值得。
- **取舍：目录重组延后**：模块化单体的物理重组收益低风险高，以测试锁定 advisor 隔离与写端口边界替代大爆炸搬迁。

## 5. 一句话总结

存量管线是好资产，全保留；一期先修「备份→迁移→身份→审计→契约」五块根基，让二三期的一切新能力从第一天起就长在持久资产项 ID 和可信底座上。

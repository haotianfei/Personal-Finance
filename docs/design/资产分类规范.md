## 1. 背景与问题

现有分类是 ADR-0001 的 EAV 方案：`attributes(id, name, type, parent_id, level, ...)` 一张表承载 `fund_type | liquidity_rating | account | owner | tag` 五种语义完全不同的维度，`asset_attributes` 把属性绑到**记录**（`asset_id`）而非**资产项**（`asset_item_id`）。

建成后用了一年，实测出五类结构性问题：

1. **基数无人保证**。`attributes` 只声明 `UNIQUE(name, type)`，不声明「一个维度一个值」。实测 138 个资产项里有 **75 个 (项, 维度) 组合存在同维多值**（同一项的 `fund_type` 同时挂两个互斥节点、`liquidity_rating` 同时挂两档）。这不是录入失误，是 schema 允许。
2. **绑定在记录级，语义错位**。分类是资产项**固有属性**（「这个账户是货币基金」），不是某次测量的属性。绑在记录上导致：同一个项 62 条记录里只有 1 条打了分类；609 个 (项, 属性) 对里只有 380 个覆盖该项全部记录，229 个只覆盖个别记录。上移到资产项级后，609 个 (项, 属性) 对摊平为项级绑定；而现状是 15,892 行记录级绑定，压缩率 96%。
3. **维度混装**。`account` 里同时装着账户、机构（银行/券商）、渠道（App/子钱包）、以及根本不是账户的东西（`现金`、`物资`、`社保账户`）。判定「在哪家机构」要靠读字符串。
4. **中间层死枝**。`fund_type` 35 个节点里有 14 个是没人会选的中间层，且节点名里嵌了全路径（`A-B-C` 当 name），`level` 与名字段数不一致。
5. **归属存真人姓名**。`owner` 只有 1 个节点且是真实姓名，「家庭池」这类保留名还会与 `attributes` 的保留名校验冲突。

结论：**问题不在数据，在 schema**。清洗数据救不了「允许同维多值」的表结构。

## 2. 设计原则

- **P1 一个维度只答一个问题**。「在哪家机构」与「从哪个入口进」是两个问题，就是两列。混在一维里，统计口径永远要写字符串匹配。
- **P2 基数由 schema 保证，不靠应用层规矩**。单值维度写成 `asset_items` 的列（`NOT NULL`），多值维度写成绑定表（`PRIMARY KEY` 去重）。应用层校验只能拦住走那个 API 的写入，拦不住脚本、迁移和手工 SQL。
- **P3 分类挂在资产项上，不挂在记录上**。分类描述身份，不描述测量。改名不重建项、分类变更不改写历史行 —— 与 `asset_items` 的身份模型一致。
- **P4 落点必须是叶子**。类别树只允许挂叶子，中间层仅用于分组展示。叶子性用触发器守（跨行约束，CHECK 表达不了）。
- **P5 宁可少一维，不要多一维**。能用一个标签表达的不建档位表；9 个稳定常量不建 lookup 表。见第 11 节。

## 3. 维度总览

| 维度 | 承载 | 基数 | 必填 | 说明 |
|---|---|---|---|---|
| 资产类别 | `asset_items.asset_class_id` → `asset_classes` | 恰好 1（叶子） | 是 | 唯一决定「这是什么东西」的维度 |
| 流动性 | `asset_items.liquidity_days` | 恰好 1（白名单值） | 是 | 数字即可排序、可聚合，不建表 |
| 机构 | `asset_items.institution_id` → `institutions` | 1 | 是 | 钱的托管方（银行/券商/基金/保险/政府/平台） |
| 渠道 | `asset_items.channel_id` → `channels` | 0 或 1 | 否 | 同一机构下多入口时才有值 |
| 归属 | `asset_items.owner_id` → `members` | 1 | 是 | 成员枚举，不存真人姓名 |
| 风险等级 | `asset_items.risk_level` | 0 或 1 | 否 | 有序标量（R1..R5），独立成列以便聚合 |
| 标签 | `asset_item_tags` → `tags` | 0..n | 否 | 横切属性（境外、退休专用、已质押…） |

`side`（asset / liability）**不是分类维度**，它是测量的符号语义（ADR-0002），存在 `assets` 上。类别树通过 `side_scope` 与它保持一致性（见第 7 节）。

**三条硬规则**：

1. `side = 'liability'` ⟺ `asset_class` 属 H 类（`side_scope='liability'`）。任一不符即触发器拒绝。
2. **风险与区域不进类别路径**。C2 里既有「境内指数」也有「境外指数」，区分靠 `risk_level` 与标签，不新增 `C2-境外` 节点 —— 否则树会随维度乘出组合爆炸。
3. **落点必须叶子**。要新增更细的区分时，先加叶子再加映射，禁止直接挂中间层。

**边界约定**（易混点，逐条固定）：

- 银行 App 里的「余额」类活期 → A1；钱包类产品自带的余额（支付平台余额、电商钱包余额）→ A3。判别：钱是否直接计息存在银行账户。
- 数字人民币钱包 → A4，即使它在某银行 App 里。
- 银行的「黄金账户」「积存金」→ D2；「实物金条」→ D1；场内或场外的黄金 ETF 及联接 → D3。
- 银行理财、券商资管、养老目标理财等**固收为主**的净值型产品 → B4；债基 → B2；货币基金 → B3。判别看产品说明书的主投方向，不看名字里的「稳」。
- 保险的**现金价值** → E4；保险的保障责任不是资产，不入账。
- 公积金账户 → E5，机构记为公积金管理中心；社保个人账户 → E1/E2，机构记为社保经办机构。**这两类不是银行账户**，不得记为 `institution.kind='bank'`。
- 信用卡未还金额、消费贷余额 → H 类，`side='liability'`，金额按**正的欠款额**记（不是负数）。

## 5. 流动性

存在 `asset_items.liquidity_days`，`INTEGER NOT NULL`，白名单：

| 档 | days | 含义 |
|---|---|---|
| L0 | 0 | 随时可用（活期、现金、钱包余额） |
| L1 | 1 | 次日（T+1 赎回） |
| L2 | 7 | 一周内 |
| L3 | 30 | 一个月内 |
| L4 | 90 | 三个月内 |
| L5 | 180 | 半年内 |
| L6 | 365 | 一年内 |
| L7 | 9999 | 一年以上 · 封闭期 |

`CHECK (liquidity_days IN (0,1,7,30,90,180,365,9999))`。

**为什么用 days 而不是档位表**：查询要回答的是「30 天内能动用多少」，`liquidity_days <= 30` 一个谓词即可；建 9 行 lookup 表只多一次 join。档位只在展示层按 days 分桶。

**不设「不可动用」档**。原方案的 L8（不可动用，days 为 NULL）会破坏 `NOT NULL` 与排序，退化为 `9999` + 标签 `锁定中` / `退休专用`。**「超长期（退休后）」也不是档位** —— 它不是流动性问题，是用途问题，用标签表达。

## 6. 机构、渠道、成员、标签

```sql
institutions(id, name TEXT NOT NULL UNIQUE,
             kind TEXT NOT NULL CHECK (kind IN ('bank','broker','fund','insurer','gov','platform','other')),
             active BOOLEAN NOT NULL DEFAULT 1)
channels(id, name TEXT NOT NULL UNIQUE, active BOOLEAN NOT NULL DEFAULT 1)
members(id, name TEXT NOT NULL UNIQUE,
        role TEXT NOT NULL CHECK (role IN ('self','spouse','joint','child','nominee')),
        active BOOLEAN NOT NULL DEFAULT 1)
tags(id, name TEXT NOT NULL UNIQUE, kind TEXT NOT NULL CHECK (kind IN ('controlled','free')))
asset_item_tags(item_id INTEGER NOT NULL REFERENCES asset_items(id),
                tag_id  INTEGER NOT NULL REFERENCES tags(id),
                PRIMARY KEY (item_id, tag_id))
```

**机构与渠道拆两维的理由**：现有 `account` 维度把「某银行」和「某银行 App 里的子钱包」混在一列，导致「按机构看合计」必须写字符串前缀匹配。拆开后 `GROUP BY institution_id` 是精确的，渠道仅在「同一机构多入口」时才有值。

**三张字典表不合并**。曾考虑 `ref_entities(id, kind, name)` 一张表加 `kind` 区分机构/渠道/成员，被否决：合并后 `asset_items.institution_id` 的外键无法约束它指向的是机构而不是成员，即伪多态，是真实的完整性洞，只为省两张小表。

**成员不存姓名**。`members.name` 存角色显示名（「本人」「配偶」「共同」「子女」「代持」），`role` 存机器语义。ADR-0011 的 `owner` 保留名「家庭池」随双向校验一并退役。

**标签分受控与自由**。`kind='controlled'` 由规范维护（起手 9 个），`kind='free'` 必须由用户在设置页显式创建，禁止录入时静默新建 —— 否则标签会退化成又一个自由文本字段。起手受控标签：`境外`、`退休专用`、`待处置`、`有抵押`、`代持`、`高波动`、`锁定中`、`税务关注`、`已质押`。

**改动留痕**：`asset_item_attr_history(item_id, dim, old_value, new_value, changed_at, changed_by, reason)` 记录七个维度的每一次变更，`dim` 取值受 CHECK 约束，表 append-only（UPDATE / DELETE 由触发器拒绝，与 `asset_item_names` 同一模式）。分类变更因此可回溯，且**不改写任何历史资产行**。

## 7. 数据库保证

| 约束 | 实现 | 理由 |
|---|---|---|
| 单值维度必填 | 4 列 `NOT NULL`（`asset_class_id` / `liquidity_days` / `institution_id` / `owner_id`） | P2 |
| 类别落点为叶子 | 触发器：插入/更新前检查该 `asset_classes` 无子节点 | 跨行约束，CHECK 不支持 |
| 类别与 side 一致 | 触发器：读 `asset_classes.side_scope`，与该项最新记录的 `side` 比较 | 跨表约束 |
| 流动性取值 | `CHECK (liquidity_days IN (...))` | 白名单即时生效，无需 lookup 表 |
| 同维多值 | 结构性不存在（单值维度是列） | P2 |
| 变更留痕只增 | `asset_item_attr_history` 上的 UPDATE / DELETE 拒绝触发器 | 与 ADR-0007 审计日志同构 |

**草稿态**：4 个 `NOT NULL` 维度会让「先建项、后补分类」的路径（截图采纳、CSV 导入）撞约束。解决方式不是放宽 `NOT NULL`，而是给 `asset_items.status` 增加 `draft` 取值：

```sql
CHECK (status IN ('active','archived','draft'))
CHECK (status = 'draft' OR (asset_class_id IS NOT NULL AND liquidity_days IS NOT NULL
                            AND institution_id IS NOT NULL AND owner_id IS NOT NULL))
```

草稿项**照常计入净值与所有合计**（ADR-0020 D1：钱是真实存在的；聚合谓词只排除归档项，不排除 `draft`），但必须在 `GET /api/analysis/summary` **单点披露**未补齐规模——`unclassified_count` / `unclassified_asset_amount` / `unclassified_liability_amount`（按 side 拆毛额 + 计数）；其余合计出口不复制字段，而是**数值必须与该 summary 精确相等**（同源不变量，ADR-0020 D4）。补齐四维即转 `active`。草稿项在界面上单列「待补分类」入口，不允许长期驻留。

## 8. 资产项名称规范

名称是**给人看的标签**，不是身份的载体（身份是 `asset_item_id`，见 CONTEXT.md「资产项」「改名」）。名称的**唯一职责是标识**，不承担描述——分类由属性列承载，写进名字就是第二个真相源。

- **格式**：`机构-产品[-区分后缀]`，段间用**半角连字符** `-`，段内禁止空格。
- **段 1 必须等于 `institution.name`**（机构维度上移后，这一点可被自动校验）。
- **大类、流动性、风险等级、归属、标签一律不进名称**。它们已是 `asset_items` 上的列，界面并排显示成列，可排序、可筛选、可按维度聚合。理由：
  - 同名信息两处存必然漂移（名字写「指数基金」而 `asset_class_id` 指向「主动权益」时无从裁决）；
  - 改一次分类就要改一次名，会把分类变动转成身份扰动，`asset_item_names` 无谓增长；
  - 名称普遍变长，列表页放不下。
- **区分后缀只在同一机构下重名时使用**，且必须是客观标识：尾号、币种、账户类型。不得用描述性文字凑区分。
- **尾号统一为独立后缀**：`-尾号NNNN`，4 位，前后不留空格。
- **括号统一半角** `()`；产品后缀（联接 A/C/E、LOF、QDII）原样保留，不作翻译。
- **禁词**：`示例`、`验证`、`测试`、`test`、`demo`。命中即为合成数据，不得进入生产库。
- **唯一性**：同一 `institution` 下归一化（NFKC + 去空格标点 + 大小写折叠）后必须唯一。

**改名不动历史**：`assets.asset_name` 是写入时的显示名快照，改名永不回写历史行（ADR-0001）。改名只追加 `asset_item_names`（append-only）。

**段数不设硬约束**。2 段（无区分后缀）与 3 段并存是常态，不是缺陷。

## 9. 从旧结构迁移的判定方法

旧库的分类不可直接信任（56% 的项与名称互相矛盾），因此迁移**不采用单一权威**，用双判据并暴露分歧：

1. **旧绑定判据**：取该项全部有效记录上的属性绑定，按**多数派**收敛（实测 75 处同维多值里只有 1 处是真并列，其余都是「头几条记录用临时分类、后来改对了」的残留）。同时计算**覆盖率 = 绑定条数 / 有效记录数** —— 覆盖率低于 50% 时判据不可信（实测大量项只有 1/62 条记录打过分类）。
2. **名称判据**：剥掉机构前缀（段 1）后按有序正则规则推定类别与流动性。**必须先剥前缀**，否则「某农业银行-活期」会因含「农业」被判成主题基金；券商机构下的个股口径直接判 C3。
3. **一致 → 高置信**；**不一致 → 取名称判据，但把两方结果与分歧方向原样写入映射表**，交人工裁决；**两方皆空 → 待裁决**。

实测结果（138 项）：高 31 / 中 80 / 低 20 / 需裁决 7；双判据分歧 79 项；名称无法推定 7 项；合成数据 5 项；归档异常 6 项；side 冲突 4 项。

**禁止自动模糊合并**。归一化后同机构内零碰撞，Levenshtein 相近的 21 对里约 19 对是正常的产品族差异（不同期限、不同编号的同类产品），自动合并会制造新的身份事故。名称相近是否同物，由人工逐条裁决。

## 10. 落地流程

1. `scripts/rebuild/s0_classify.py`（只读旧库）生成三份产物：`attr_mapping.csv`（旧属性 → 新结构逐条去向）、`item_classification.csv`（138 项 × 六维 + 双判据分歧 + 空裁决列）、`classify_report.md`（分布与分歧清单）。产物含真实名称，落 `data/rebuild/`（gitignore，不入库）。
2. 人工在 `item_classification.csv` 的 `裁决_*` 列逐项签字。**未签字的行按「名称判据」执行，且标记保留**。
3. `0026_asset_classification_refactor.py` 建 7 张新表、`asset_items` 加 6 列、建 3 个触发器、删除 `attributes` 与 `asset_attributes`。
4. 导入脚本按裁决表写分类，并为每一项补一条 `asset_item_attr_history` 的 `reason='rebuild_from_eav'` 基线记录。
5. 验收：全部 `active` 项四维非空、全部类别为叶子、`side` 与 `side_scope` 全一致、`CHECK` 与触发器实测生效（造违例行必须被拒）。

## 11. 明确不做的事

- **不建 `liquidity_ratings` 档位表**：9 个稳定常量，建表只增加 join。档位名在展示层由 days 推导。
- **不建 `asset_item_extra` 草稿区**：草稿态用 `status='draft'`，不另开一张表承接「还没填完」的维度。YAGNI。
- **不建 `ref_entities` 合并字典**：伪多态，外键无法约束目标类别（见第 6 节）。
- **不拆资产/负债两棵类别树**：一棵树 + `side_scope` 就够；拆两棵会让「同一产品既是资产也可能是负债」（如贵金属积存账户的透支）无法表达。
- **不把风险等级做成标签**：R1..R5 是有序标量，标签是无序集合。要能算「加权平均风险等级」就必须是列。
- **不把「境外」做成维度**：它是布尔标签，二维交叉会让类别树按地区复制一遍。
